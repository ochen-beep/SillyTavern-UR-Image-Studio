# Вынос данных URIS из `settings.json` в серверные файлы

**Дата:** 2026-09-12
**Ветка:** feat/inline-engine
**Статус:** в работе

## Проблема

`settings.json` SillyTavern разросся до 7,81 МБ. Из них 4,81 МБ — расширение
`ur_image_studio`, почти целиком `imageConnections.galleryIndex` (711 записей).

Причина не в объёме истории как таковой, а в том, что данные лежат не в том
хранилище. Официальная документация ST («Best Practices» → *Don't store large
data in extensionSettings*):

> Extension settings are loaded into memory and saved frequently. Large data can
> cause performance issues.

Механизм, подтверждённый по исходникам ST 1.18.0:

- `public/script.js:8051` — `saveSettings()` собирает **весь** объект настроек
  Таверны и POST'ит его на `/api/settings/save`;
- `src/endpoints/settings.js:209` — сервер пишет его целиком через
  `JSON.stringify(request.body, null, 4)` (отсюда ~1,94 МБ отступов);
- `public/script.js:470` — `saveSettingsDebounced` = debounce 1000 мс, общий для
  всех расширений;
- merge и lock отсутствуют: побеждает последний записавший.

Итог: любая правка любой настройки любым расширением перезаписывает все 7,81 МБ,
включая 4,8 МБ галереи URIS.

## Правило размещения

Один вопрос на каждую сущность: **«если эти данные потерять — что произойдёт?»**

| Ответ | Ведро | Где физически |
|---|---|---|
| Сломается конфиг | Настройки | `extensionSettings` |
| Пропадёт моя работа | Данные | серверный файл (user-files API) |
| Пересчитается само | Кэш | localforage |
| Относится к чату | Чат | `chatMetadata` |

## Целевое состояние

```
data/<user>/user/files/
  uris_templates.json   — уже есть (эталон паттерна)
  uris_gallery.json     — НОВОЕ: карточки галереи
  uris_refs.json        — НОВОЕ: пул референсов + папки
  uris_presets.json     — НОВОЕ: пресеты параметров
```

В `extensionSettings.ur_image_studio` остаются только настройки: флаги, enum'ы,
`windowGeometry`, `accordionState`, `inlineTriggers`, `globalGenerationDefaults`,
`selectedRouteId`, `connections` (без данных), `apiSource`/`profileId`.

Не трогаем (уже правильно): `chatMetadata` (`uris_binding`, `uris_inline`),
localforage (история, черновики, recovery, event-log), API-ключи.

## Архитектура: один generic-модуль

Потребители уже абстрагированы за интерфейсом `{list, create, update, delete}`
(`refs-library.js:41`, `param-presets.js:26`, `prompt-templates.js:63`) либо за
двумя функциями `index()`/`persist()` (`gallery-index.js:42,48`). Поэтому
переписывать потребителей не нужно — нужно подставить другой бэкенд.

`src/file-store.js` — generic, инкапсулирует: пробу эндпоинта, загрузку и
миграцию, зеркало, сериализованную цепочку записей, keepalive-flush, режим
`legacy` (работа на настройках при недоступном user-files API), диагностику и
логирование. То же, что уже делает `template-file-store.js`, но переиспользуемо.

### Контракт

```js
createFileStore({
  name,            // 'uris_gallery.json' — ASCII, см. ограничения
  version,         // версия документа
  key,             // имя свойства в документе: { v, <key>: value }
  empty,           // () => начальное значение
  legacyRead,      // () => значение из настроек (или null)
  legacyWrite,     // (value) => запись в настройки (режим legacy)
  legacyStrip,     // () => удалить копию из настроек (freedBytes)
  resolveLoad,     // ({ fileValue, fileParsed, legacyValue }) => { value, migrate }
  stripLegacyOnLoad, // bool — удалять ли копию после успешной загрузки
  keepaliveLimit,  // по умолчанию 60 КБ
}) → {
  ready(), mode(), snapshot(), mutate(fn), replace(v),
  flush(), flushOnUnload(), footprint(), diagnostics(),
}
```

## Нюансы, которые учтены

1. **Порядок миграции.** Сначала запись файла → `await` подтверждения → только
   потом очистка копии в настройках. При ошибке копия остаётся, миграция
   повторяется на следующем запуске (идемпотентно). Образцы: `template-file-store.js:149-159`,
   `feed-file-store.js:629-647` (DS Comments).
2. **Strip обязателен для крупных стораджей.** `template-file-store` намеренно
   оставляет копию шаблонов в настройках как фолбэк для даунгрейда — для 3 КБ это
   нормально, для 4,8 МБ это обнулило бы весь выигрыш. Поэтому
   `stripLegacyOnLoad` — настройка на стор: `false` для шаблонов (поведение не
   меняется), `true` для галереи/refs/пресетов.
3. **Никогда не терять данные при конфликте «файл пуст, в настройках данные».**
   `resolveLoad` по умолчанию объединяет по `id` (база — файл, добавляются
   отсутствующие записи из настроек). Это идемпотентно и безопасно.
4. **Битый файл = отсутствующий.** Ошибка `JSON.parse` или несовпадение версии →
   трактуем как «файла нет» и мигрируем из настроек, а не падаем.
5. **Режим `legacy`.** Если `/api/files/verify` недоступен (старая ST) —
   расширение продолжает работать на настройках. Обязательно для совместимости.
6. **Синхронные читатели.** `gallery-index.countCardsByImagePath` синхронный;
   работает от зеркала, поэтому все async-точки входа обязаны сначала
   `await ready()`. Зеркало прогревается на старте в `init()`.
7. **`reconcileCards` перестаёт писать всегда.** Сейчас он вызывает `persist()`
   безусловно (`gallery-index.js:180`), из-за чего открытие вкладки «Галерея»
   пересобирает 4,8 МБ и заказывает POST настроек. Будем писать только если
   состояние реально изменилось.
8. **Keepalive ограничен ~64 КБ.** Для `uris_gallery.json` (~800 КБ после чистки)
   unload-flush не сработает — это логируется как `skipped`, а надёжность
   держится на обычной записи через цепочку. Мелкие стораджи флашатся.
9. **Конфликт двух вкладок.** Остаётся last-writer-wins (как и сейчас с
   настройками) — регрессии нет. Логируется, но не решается: усложнение не
   оправдано.
10. **Имена файлов только ASCII** — `validateAssetFileName`
    (`src/endpoints/assets.js:21-24`) разрешает `[a-zA-Z0-9_\-.]+`.
11. **API перечисления `user/files` нет** — только `verify` и статичный `GET`.
    Поэтому индексный файл всё равно нужен.
12. **`bodyParser.json({ limit: '500mb' })`** (`src/server-main.js:110`) — лимит
    не мешает.

### Отклонения от плана

**Фаза 5 (`catalogs`) не сделана.** `imageConnections.catalogs` — действительно мёртвый
ключ (объявлен в `src/core.js:30`, не читается и не пишется нигде), но он пустой и
занимает ~12 байт, так что к проблеме размера отношения не имеет. Удаление — отдельная
гигиеническая правка, которая ничего не улучшает в рамках этой задачи и добавляет риск
для совместимости бэкапов. Оставлено как есть, зафиксировано как находка.

**Фаза 2b отложена.** Дедупликация промптов по хэшу (~1,7 МБ из 4,8 МБ) и удаление
`provenance.route` (~494 КБ) уменьшили бы `uris_gallery.json`, но не влияют на главный
результат — выход из `settings.json` уже достигнут. Обе правки требуют второго слоя
трансформации в пути данных карточки (гидратация/дегидратация в `gallery-index.js`), а
`provenance.route` — это диагностика, которую проект кладёт сознательно; удалять её
попутно с переездом хранилища неправильно. Отдельная задача; в `src/file-store.js` для
неё уже есть всё нужное (`mutate(..., {persist:false})`, инкрементальная запись).

### Что осталось проверить на живой инсталляции

Тестами покрыта логика, но не реальный сервер ST. На живой таверне стоит убедиться:
1. Панель «Хранилище» в Настройках показывает режим «файл» для всех четырёх сторов.
2. Строка «settings.json (модуль)» после первого запуска — сотни КБ вместо мегабайтов.
3. Файлы реально появились в `data/<user>/user/files/`.
4. Карточки галереи, референсы и пресеты на месте после перезагрузки страницы.
5. «Экспорт данных» → «Импорт данных» возвращает пул и пресеты (round-trip покрыт
   тестом на моке, но не на живом сервере).

## TECH DEBT — к удалению в будущих релизах

Проверено на живой инсталляции 2026-09-12: `settings.json` 7,81 МБ → 1,98 МБ,
модуль URIS 4,81 МБ → 312 КБ. Ниже — что в этой работе временное и по какому
признаку это можно снять.

Здесь **два разных механизма с разными триггерами удаления**, и путать их нельзя:
один уходит сам после того, как все пользователи один раз загрузятся, второй живёт
столько, сколько поддерживается старая SillyTavern.

### TD-1: одноразовая миграция «настройки → файл» — удалять после прогрева базы

Что это: `legacyRead` / `legacyStrip` в четырёх стораджах, ветка миграции в
`file-store.js` (`detectAndLoad`), `stripLegacyOnLoad`, а также два «подкладывания
живых значений» в `data-port.js` (`getRefsForExport` / `getParamPresetsForExport` /
`getTemplateRecordsForExport` и парные `replace*Records`).

Почему временное: после первого успешного запуска копии в `extensionSettings`
удалены, `legacyRead` возвращает null, и код миграции не исполняется никогда.
В логах живого теста это уже видно: при повторной загрузке события
`store-strip` идут с `freedBytes: 0`.

Когда удалять: не раньше, чем через один-два релиза, и только если принято
решение не поддерживать прыжок через эти версии. Если пропустить удаление
слишком рано, пользователь, обновившийся с релиза до переезда, потеряет галерею,
референсы и пресеты — копии в настройках останутся, но читаться не будут.

Прецедент в проекте уже есть: `MIN_BACKUP_VERSION` в `data-port.js` с явным
списком отставленных форматов бэкапа (v2–v5) — тот же приём, тот же комментарий-обоснование.

Что оставить навсегда: структурные события `store-*` в диагностике (они бесплатны
и это единственный способ разобрать инцидент хранилища постфактум).

### TD-2: режим `legacy` (работа на настройках) — удалять по версии ST

Что это: `mode === 'legacy'` и `legacyWrite` во всех стораджах, ветка
`safeLfKey`-подобных фолбэков, отдельные ветки в `prompt-templates.js`
(`legacyStore()`).

Почему не то же самое, что TD-1: это совместимость, а не миграция. У пользователя
на старой ST расширение должно продолжать работать, а не падать.

Когда удалять: когда минимальная поддерживаемая версия ST гарантирует наличие
user-files API. Сейчас поддерживается 1.18.x, а нужные роуты
(`/api/files/upload`, `/api/files/verify`, `GET /user/files/*`) там есть —
значит триггер уже выполнен, но удаление лишнего пути снижает устойчивость
без выигрыша. Приоритет низкий.

### TD-3: визуал миграции — не существует

Отдельного UI миграции не делалось: перенос происходит молча на старте
(`index.js`, `init()` → `ensure*StoreReady()`), а единственный визуальный элемент —
панель «Хранилище» в Настройках. Она **не** часть миграции, а диагностика
(см. вопрос про её нужность ниже). Удалять вместе с TD-1 нечего.

### Незакрытые находки, связанные с этим переездом

Не техдолг, а задачи — каждая меняет поведение, поэтому не делались попутно:

1. **`connections[].detected` — 207 КБ из оставшихся 319 КБ.** Это кэш
   модельных каталогов (`detected.modelIds`, 343 модели на одно подключение),
   то есть по правилу размещения — localforage, а не настройки. Пользовательская
   конфигурация подключения там же занимает ~11 КБ. Самая крупная оставшаяся
   утечка; чинится тем же `createFileStore`/localforage без новой механики.
2. **Копия `templates` в настройках — 98 КБ.** Оставлена сознательно
   (`stripLegacyOnLoad: false`) как фолбэк для даунгрейда, но логи живого теста
   показывают `orphans: 2`: копия уже разошлась с файлом, то есть даунгрейд
   получил бы устаревший набор. Либо снимать копию вместе с остальными, либо
   перестать это логировать как предупреждение на каждой загрузке.
3. **Удаление чата не чистит галерею.** ST эмитит `CHAT_DELETED` и
   `GROUP_CHAT_DELETED`, URIS их не слушает: карточки удалённого чата остаются в
   индексе и на диске навсегда, просто становятся невидимыми (галерея
   фильтруется по `provenance.chatId`). Это было и до переезда, но с ростом
   галереи становится дороже.
4. **Запись галереи — целиком файл, дважды на генерацию.** Логи:
   `store-write … 3063506 bytes, ms=76` и сразу `3063597 bytes, ms=89` —
   `addCard` + `updateCard(thumbPath)`. Дедупликация промптов по хэшу и/или
   разбивка индекса по чатам (или файл на карточку) убирают основную часть.



## Логирование для проверки

Каждый переход пишется **дважды**: в `log()` (консоль) и в
`recordDiagnosticEvent()` (попадает в «Экспорт диагностики»). Имена полей
выбираются так, чтобы не попасть под редакцию `diagnostic-events.js:69`
(ключи `prompt`, `body`, `response` маскируются).

| Событие | Поля | Зачем |
|---|---|---|
| `store-mode` | `store, mode, probe` | выбран файл или legacy |
| `store-load` | `store, result, entries, bytes, ms` | что прочитали |
| `store-migrate` | `store, entries, bytes, source` | миграция из настроек |
| `store-strip` | `store, freedBytes` | **сколько освободили в settings.json** |
| `store-write` | `store, result, entries, bytes, ms` | запись удалась/нет |
| `store-write-skipped` | `store, reason` | запись не нужна/невозможна |
| `store-unload-flush` | `store, result, bytes` | `sent` или `skipped` |
| `store-footprint` | `settingsBytes, imageConnectionsBytes, galleryIndexEntries` | **главная метрика: сел ли settings.json** |

Ключевая проверка результата: `store-footprint` до и после. Ожидаем падение
`settingsBytes` с ~7,8 МБ до ~0,3 МБ.

## UI: панель «Хранилище»

В `tab-settings.js`, в секции «Данные и диагностика» — read-only таблица: имя
стора, режим (`файл`/`настройки`), записей, байт, результат последней записи.
Плюс строка «Объём настроек» с байтами и числом карточек в индексе. Это то, чем
пользователь проверяет работу системы без консоли.
