# Дизайн: хранилище галереи v2 — карточка как файл

**Дата:** 2026-09-12
**Ветка:** feat/inline-engine
**Статус:** дизайн утверждён устно, ждёт ревью документа
**Предыдущая работа:** `2026-09-12-storage-externalization.md` (вынос галереи из settings.json — выполнен)

## 1. Цель

Хранилище галереи, у которого **стоимость записи одной карточки не зависит от того,
сколько карточек уже есть**, и которое незаметно пользователю: без новых экранов,
без смены привычек, без потери данных при любых действиях.

Замеры текущего состояния (713 карточек, 2,93 МБ, одна инсталляция):

```
JSON.parse 2,93 МБ      8.9 мс
structuredClone         12 мс
запись на генерацию     76–89 мс × 2
загрузка на старте      117 мс (блокирует init())
```

Проверено на сценарии **100 картинок в день** (36 500 в год), ради которого дизайн
пересматривался: один общий файл к концу года — 157 МБ и ~4 секунды на запись.
Глобальный дайджест — 5,5 МБ и 130 мс, растёт без остановки. Оба не годятся:
их стоимость записи зависит от объёма.

## 2. Решённые продуктовые вопросы

Решения приняты в диалоге и фиксируются как часть дизайна.

**Р1. Промпты — ценная работа** («B»). Тексты промптов нельзя терять при
рефакторинге хранилища. Следствие: у карточки есть своё хранилище полезной
нагрузки, а всё восстановимое — отдельно.

**Р2. Галерея — журнал генераций URIS** («A»). Механизм `reconcileCards`,
автоматически импортирующий чужие картинки как фантомные карточки, удаляется.
Замер: 149 фантомов из 713 не показываются ни в одном чате, потому что у них
`provenance` — строка `'native'`, а фильтр требует `provenance.chatId`.

**Р3. URIS не удаляет файлы картинок** («A»). Убирается `/api/images/delete`,
а вместе с ним `countCardsByImagePath` и `isReferencedByPool` — оба существовали
только ради защиты удаляемого файла, и первый был синхронным O(n)-читателем.
Кнопка «удалить» в галерее убирает только карточку; файл остаётся в папке
персонажа и в родной галерее ST, где для этого есть свой интерфейс.

**Р4. Путь картинки — стабильный ключ** («A»). Пользователь не переименовывает и
не переносит файлы. Проверено: все 713 имён — ASCII (`uris_<uuid>.png`).

**Р5. Принятие внешних картинок.** Импорт делается явным действием пользователя
из экрана «Архив», не автоматикой — это не противоречит Р2, который запрещает
именно невидимый автоимпорт. Замер: в папках генераций **1 882 картинки, из них
1 175 без карточки** — 992 от `sillyimages-compare` (префикс `iig_`), 179 —
собственные генерации URIS с потерянными карточками.

**Р6. Экран без персонажа = «Архив».** Фильтр галереи по `chatId` прячет
**281 карточку из 713 (39%)**: 132 в удалённых чатах (среди них 85 и 42 карточки
из чатов `Jax Sterling The Heirs` от 15 августа) и 149 без `chatId`. На экране
без персонажа фильтр по чату не применяется по определению — там показывается
весь архив. Сироты при этом **не детектируются**: список живых чатов стоит
~100 запросов (`/api/chats/search` по одному персонажу), а удалённый чат и так
виден по своему сырому идентификатору в заголовке группы.

**Р7. Флаг `hidden` удаляется.** Он появился как защита записи при возможном
удалении файла (Р3) и при автоимпорте (Р2) — обе причины исчезли. «Убрать»
теперь означает убрать карточку; картинка остаётся и возвращается через поиск
(Р5). Существующие 137 скрытых карточек при миграции становятся обычными.

## 3. Архитектура

Два вида файлов, оба — обычный JSON в `data/<user>/user/files/`.

```
сайдкар      uris_c_<ключ>.json        один на карточку, пишется один раз
индекс       uris_idx_<hash8>.json     один на папку персонажа, только сетка
```

**Инвариант: одна картинка — одна карточка.** Каждая генерация создаёт свой
файл, поэтому дублей пути нет. Следствие: не нужны защита разделяемых путей и
проверка использования файлом референсами.

**Правило разделения:** сайдкар хранит всё про одну генерацию; индекс хранит
ровно то, без чего нельзя нарисовать сетку, не читая сайдкары.

**Индекс — чистый кэш.** Всё его содержимое выводится из листинга папок плюс
сайдкаров, поэтому его порча или потеря безвредна: пересборка — та же кнопка
«найти», ~26 запросов. Это снимает вопрос целостности целиком.

**Следствия, зафиксированные как свойства, а не как баги:**

- Конфликт двух вкладок перестаёт быть потерей данных: у каждой вкладки свой
  индекс в памяти, «последний победил» может потерять запись дайджеста, но
  сайдкар на месте и карточка возвращается поиском.
- Порядок записи обязателен: **сначала сайдкар, потом индекс**. Сбой индекса
  лечится поиском; сбой сайдкара означал бы потерю промпта, которого ещё нет
  нигде. Сайдкар ~4 КБ, то есть попадает под лимит `fetch keepalive` (~64 КБ) —
  упавшая запись повторяется на `pagehide`.
- Принятые карточки имеют сайдкар тоже (маленький, с `origin` и `chatId`).
  Раньше предлагалось держать их только в индексе, но тогда потеря индекса
  стирала бы принятые карточки — теперь все карточки устроены одинаково.

## 4. Модель данных

### Сайдкар `uris_c_<ключ>.json`

```json
{ "v": 1, "card": {
    "imagePath":  "user/images/Mason%20Alt/uris_x.png",
    "prompt":     "…",
    "connectionId":  "mtsfvu4bu6otqy",
    "connectionName": "Nano Banana",
    "modelId":    "openai/gpt-image-2",
    "generationContract": "openai-images",
    "aspectRatio": "1:1", "imageSize": "1K", "quality": "auto",
    "chatId": "…", "sourceMsgId": 42, "requestId": "req-1",
    "referenceIds": ["…"],
    "width": 1024, "height": 768,
    "origin": "generated",
    "createdAt": 1730000000000,
    "output": { "bytes": 12345, "mime": "image/png" }
} }
```

`origin` — `generated` (создано URIS) или `adopted` (принято из папки).
`connectionName` — снимок имени на момент генерации: соединение можно переименовать
или удалить, а бейдж обязан оставаться правдивым. `requestId` сохраняется — это
ключ стыковки карточки с журналом диагностики.

Уходят по замерам (713 карточек): `stage2Snapshot`, `negativePrompt`, `refs`,
`refsSig`, `style` — пусты на всех; `routeId` — выводится из `generationContract`
плюс `modelId`; `status` — заменяется на `onerror` картинки; `updatedAt` —
сайдкар неизменяем.

Из `provenance` (451 КБ) остаётся только `output` в сокращённом виде. Уходят:
`route` (328 КБ — дубль журнала диагностики), `chatId` (29,5 КБ — есть в самом
сайдкаре), `characterFolder` (9,7 КБ — выводится из `imagePath`). `requestId`
и `sourceMsgId` переезжают на верхний уровень.

### Индекс папки `uris_idx_<hash8>.json`

```json
{ "v": 1, "folder": "Mason Alt", "cards": [
    { "imagePath": "user/images/Mason%20Alt/uris_x.png",
      "thumbPath": "user/images/URIS_Thumbs/uris_x_thumb.webp",
      "width": 1024, "height": 768,
      "chatId": "…", "createdAt": 1730000000000,
      "modelId": "openai/gpt-image-2", "connectionName": "Nano Banana",
      "origin": "generated" }
] }
```

Массив отсортирован по `createdAt` по убыванию. Порядок полей — те, что нужны
сетке: путь и превью для отрисовки, размеры для раскладки, `chatId` для
фильтра «только этот чат», бейджи для превью. Промпт здесь не хранится.

## 5. Имена файлов и вывод ключей

**Ключ карточки — `imagePath`.** От него детерминированно выводится имя сайдкара.

```
sidecarOf(imagePath) = 'uris_c_' + basename без расширения + '.json'
                       — если результат проходит /^[A-Za-z0-9_\-.]+$/;
иначе 'uris_c_' + fnv8(imagePath) + '.json'
```

`fnv8` — FNV-1a 32-бит, 8 hex-символов; тот же алгоритм, что уже используется в
`hashDiagnosticId` (`src/diagnostic-events.js`), переиспользуется оттуда.

Проверено: все 713 имён проходят проверку напрямую, так что имя остаётся
читаемым — `uris_c_e16747ec-c7ec-….json`. Фолбэк на хэш нужен для чужих файлов
с кириллицей или пробелами (`sillyimages-compare` имена не меняет, но папка
`Taylor Hughs ║ Dating Rumors` показывает, что не-ASCII встречается).

**Индекс папки** выводится из папки:

```
indexOf(folder) = 'uris_idx_' + fnv8(folder) + '.json'
```

Имя непрозрачно намеренно: имена папок не-ASCII (`Код-кун`, `Taylor Hughs ║
Dating Rumors`), а `validateAssetFileName` требует ASCII. Чтобы файл можно было
опознать, внутри лежит поле `folder` с настоящим именем.

**Нахождение сайдкара не требует индекса:** зная путь картинки, имя вычисляется.
Обратное тоже верно — перечислив папки, можно найти все сайдкары. Поэтому ни один
файл не является единственным источником правды о существовании другого.

## 6. Поток записи

**Генерация** (`image-api.js`, после материализации картинки):
1. записать сайдкар (4 КБ, awaited, с ретраем и keepalive-флашем при сбое);
2. дописать карточку в индекс папки и перезаписать его;
3. миниатюра — фоновая задача, как сейчас, с записью `thumbPath` в индекс.

**Убрать карточку:** удалить сайдкар и запись индекса. Файл картинки остаётся.
Кнопка подтверждает действие и сообщает, что картинка останется, а вернуть
можно поиском. Промпт при этом теряется — это осознанное следствие отказа от
флага `hidden`: обратимое «спрятать» вернуло бы флаг обратно.

**Принять картинку** (экран «Архив»): записать сайдкар с `origin: 'adopted'`
(без промпта — взять его неоткуда, см. ниже) и добавить в индекс. Оба действия —
для пачки, с прогрессом и возобновлением через `verify`.

**Миниатюры:** у 620 карточек из 713 их нет, потому что миниатюры появились
8 сентября, а карточки копились с июня. Сетка при отрисовке карточки без
`thumbPath` ставит её в очередь бэкфилла: по одной, только видимые на экране,
запись `thumbPath` в индекс по завершении.

**Размеры:** `width`/`height` есть только у 205 карточек. Недостающие берутся
из `img.naturalWidth` после загрузки превью и дописываются в индекс один раз
за сессию (debounce), чтобы не писать на каждый скролл.

## 7. Поток чтения

**Галерея в чате.** Сетка построена из индекса папки этого персонажа — папка
определяется существующим `getCharacterImageFolder()` (`src/native-image-storage.js`):
имя персонажа для обычного чата, `group_<id>` для группового. Пейджинация
обязательна: при 100 картинках в день папка переваливает за тысячи записей.
Промпт и полный набор полей читаются из сайдкара при открытии карточки (один GET).

**Область видимости — папка персонажа, не чат.** Фильтр «только этот чат»
остаётся доступным переключателем (chatId есть в индексе), но по умолчанию
галерея показывает все генерации персонажа: фильтр по чату — это то, что сейчас
прячет 39% архива, и при 100 картинках в день он прятал бы всё больше.

**Архив (экран без персонажа).** Те же данные без фильтра по чату, сгруппированные
по `chatId` (у удалённых чатов виден сырой идентификатор — он достаточно читаем:
`Jax Sterling  The Heirs - 2026-08-15@20h33m42`). Здесь же — кнопка «найти
картинки без карточек». Отдельного представления «скрытое» после отказа от флага
нет: архив показывает все карточки, включая ранее скрытые, — при миграции они
становятся обычными.

**Поиск непринятых картинок:**
1. `POST /api/images/folders` — список папок (1 запрос);
2. пользователь выбирает папки, служебные (`URIS_Thumbs`, `URIS_Refs`, `iig_refs`)
   сняты по умолчанию;
3. `POST /api/images/list` на каждую выбранную (~25 запросов);
4. `POST /api/files/verify` пачкой по выведенным именам сайдкаров (1 запрос) —
   каких нет, те и принимаем.

Итого полный обход архива — около 27 запросов. Ничего не записывается до
подтверждения пользователем.

## 8. Обработка ошибок

| Ситуация | Поведение |
|---|---|
| Сайдкар не записался при генерации | ретрай через цепочку, затем keepalive-флаш на `pagehide`; карточка всё равно попадает в индекс — иначе её не было бы видно |
| Сайдкар отсутствует у карточки из индекса | карточка рисуется по картинке, промпт недоступен, кнопки «копировать» и «перегенерировать» скрыты; событие в диагностику |
| Индекс папки потерян или побит | пересборка: листинг папки + `verify` сайдкаров + чтение сайдкаров; безвредно, потому что индекс — кэш |
| Картинка удалена вне URIS | `onerror` на `<img>` — карточка помечается «файл утерян», промпт сохраняется |
| Две вкладки пишут одновременно | «последний победил» на уровне индекса; потерянная запись возвращается поиском, сайдкары не затрагиваются |
| `user-files` API недоступен | режим `legacy`: галерея продолжает работать на текущем одном файле, как сейчас |

## 9. Миграция

Одноразовая, из текущего `uris_gallery.json` (v1, 713 карточек с промптами).

1. прочитать v1;
2. для каждой карточки записать сайдкар и собрать запись индекса её папки;
3. записать индексы по папкам;
4. удалить v1 — **только после** того, как `POST /api/files/verify` подтвердил
   наличие всех сайдкаров.

Свойства: возобновляемая по построению (проверка через `verify` говорит, какие
сайдкары уже записаны); идемпотентная; не блокирует `init()` — идёт в фоне,
а вкладка «Галерея» и «Архив» показывают прогресс, пока она не закончилась.
До завершения миграции промпт читается с фолбэком из v1-документа — это
единственное место с двумя источниками, оно существует ровно до конца миграции
и удаляется вместе с ней.

Скрытые карточки при миграции становятся обычными: флага больше нет.

## 10. Логирование

События пишутся и в консоль, и в журнал диагностики (`stage: 'storage'`).
Имена полей выбраны вне списка маскирования `diagnostic-events.js`
(`prompt`, `body`, `response`).

| Событие | Поля | Зачем |
|---|---|---|
| `card-write` | `folder, result, bytes, ms` | запись сайдкара |
| `card-remove` | `folder, result` | убрана карточка |
| `card-adopt` | `folder, result, origin` | принятая картинка |
| `idx-write` | `folder, result, cards, bytes, ms` | запись индекса папки |
| `idx-rebuild` | `folder, cards, ms` | пересборка индекса |
| `scan-run` | `folders, images, unadopted, ms` | обход архива |
| `migrate-run` | `result, done, total, ms` | миграция v1 → v2 |

Ключевая проверка на живой инсталляции: размер `settings.json` (уже ~312 КБ,
дальше не меняется), число файлов в `user/files/` (растёт вместе с архивом),
и отсутствие `store-write` с байтами порядка мегабайт — их быть не должно.

## 12. Сознательно не делается

- **Разбивка индекса по месяцам.** Утверждалась в диалоге, снята после расчёта:
  100 картинок в день на **одного** персонажа дают 5,5 МБ индекса и 130 мс записи
  к концу года — незаметно. Разбивка требует либо манифеста, либо перебора месяцев
  через `verify`, плюс двусоставного чтения. Возвращаться к ней стоит по триггеру:
  индекс папки превысил ~5 МБ или запись ~200 мс. Механизм миграции тогда тот же.
- **Дедупликация промптов по хэшу** (−0,6 МБ). Слой разворачивания на пути чтения
  промпта ради 20% размера. Если понадобится — добавляется к сайдкару локально,
  не затрагивая индекс.
- **Экспорт промптов в бэкап URIS.** Сайдкары лежат в `data/<user>/user/files/`
  и попадают в штатный бэкап данных SillyTavern. Свой «Экспорт данных» галерею
  не выгружает, как и раньше — это осознанное ограничение.
- **Постраничный рендер с виртуализацией.** Нужен обязательно, но это работа
  по интерфейсу, а не по хранилищу; делается отдельно, иначе сливается с ней.
- **Чтение промпта из PNG-метаданных принятых картинок.** Проверено на живых
  файлах: `iig_*` не содержат текстовых чанков с промптом (только IPTC/XMP от
  ImageMagick), а `sillyimages-compare` промпты в доступном виде не хранит.
