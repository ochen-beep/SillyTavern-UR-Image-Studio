## 2026-09-22 — v0.9.2: платный текстовый POST больше не перепосылается вслепую (DELIVERY_AMBIGUOUS + разведка пути доставки)

Закрытие находки deep-review о двойном биллинге: CORS-маскированный сбой («сервер обработал и ответил 200 без CORS-заголовков») неотличим для JS от «запрос не ушёл» (MDN, whatwg/fetch#443), и реактивный ретрай такого сбоя мог списать оплату дважды. Для Stage 2 (платные картинки) защита уже стояла (`noResubmit` → `IMAGE_DELIVERY_AMBIGUOUS`); дыра оставалась в Stage 1 — текстовые POST «своего» источника через `autoFetch` (providers/openai.js, providers/gemini.js). Полный набор зелёный (1324).

- **`autoFetch` стал методо-осознанным** (`src/proxy.js`): для POST отключены все три автоперепосылки — прямой→прокси на неизвестном хосте, флип direct→proxy у известного direct-хоста и обратный флип proxy→direct. Вместо них кидается типизированная `DELIVERY_AMBIGUOUS` (код + `noRetry`) с честным текстом «запрос мог быть обработан провайдером, автоматически не повторяется», а кэш стратегий переводит хост в 'proxy' — следующая попытка уходит через прокси сразу, без жертвенной прямой попытки. GET-ветки (скачивание картинок, каталоги, файлы референсов) не изменились: для идемпотентных запросов исторический гибридный фолбэк безопасен и сохранён.
- **Разведка пути до первого платного запроса** (новый `probeDeliveryStrategy` в `src/proxy.js`, вызывается из обоих текстовых провайдеров): перед POST к неизвестному хосту делается один дешёвый GET списка моделей с теми же заголовками; любой HTTP-ответ (даже 401) доказывает direct-доставку, CORS-TypeError переводит хост в 'proxy' — и первый платный запрос сразу идёт верной дорогой. Best-effort: неудача разведки (кроме отмены) не блокирует генерацию.
- **`callWithRetry`** (`src/core.js`): ошибки с пометкой `noRetry` не ретраятся никогда (чтобы «исход неизвестен» не умножался настройкой «повторов»), а из ретраебельного regex убрано слово «unavailable» — оно совпадало с текстом собственной обёртки провайдеров («Text API is unavailable: …») и ретраило любой завёрнутый сбой. Статус-кодовые ретраи 429/5xx сохранены: ответ доказан, повтор безопасен (практика openai-node/got).
- **Провайдеры** (`src/providers/openai.js`, `src/providers/gemini.js`): типизированная ошибка проводится наружу как есть — не переклеивается в «unavailable» и не ретраится.
- **Тесты**: контракты POST-фолбэков в `tests/proxy.test.js` переписаны под новую семантику (плюс новые GET-варианты, закрепляющие сохранённый фолбэк), 5 кейсов `probeDeliveryStrategy` включая интеграцию «разведка → POST сразу через прокси», `tests/text-provider-delivery.test.js` — фантомный CORS у обоих провайдеров даёт ровно один POST и честную ошибку, `tests/retry-policy.test.js` — noRetry и убранный «unavailable».
- Замечание о границах: типичный CORS-блок срабатывает на этапе preflight (POST вообще не отправляется — повтор безопасен), так что чинимое окно — редкие «200 без заголовков» и обрывы связи на долгих генерациях; это гигиена, а не пожар (обсуждение и сурвей практик — `docs/2026-09-22-deep-review.md`, раздел о биллинге).

## 2026-09-12 — v0.8.6: защита файловых стораджей от разрушающих сценариев (само-ревью хранения)

Итог ревью системы хранения (`file-store.js` + потребители) с проверкой по исходникам ST 1.18+ (`src/endpoints/files.js`, `src/endpoints/data-maid.js`) и сверкой с тестами. Три дыры вели к молчаливой потере данных, две — к деградации. Все фиксы покрыты тестами; полный набор зелёный (1212).

- **F1 — сбой чтения при старте больше не может стереть файл** (`src/file-store.js`). Раньше: `GET /user/files/…` упал не-404 (500, сетевой обрыв) → mirror строился с пустой базы в режиме `file` → первая же мутация перезаписывала серверный файл одним элементом (713 карточек → 1). Теперь: флаг `unreadableFile`; перед первой записью цикл перечитывает файл — 404 (файла точно нет) → пишем; файл есть → запись блокируется на сессию (`writeBlockedReason`), пользователь получает тост «перезагрузите страницу», в диагностике `store-write-skipped` с reason `file-unreadable-at-load`; сервер всё ещё недоступен → payload ждёт следующей мутации, ничего не отправляется. Keepalive-flush на выгрузке тоже уважает блок.
- **F2 — документ от более новой версии расширения читается, но не «чинится»** (`src/file-store.js`, `src/ui/tab-settings.js`, `style.css`). Раньше любой `doc.v !== version` считался corrupt → init немедленно перезаписывал файл пустым/legacy-набором: откат расширения на предыдущий релиз = уничтожение данных, записанных новым. Теперь `doc.v > version` → режим `readonly`: содержимое грузится best-effort, запись отключена с тостом «обновите расширение», настройки не стрипаются; `doc.v < version` — прежний corrupt-ремонт. Панель «Хранилище» показывает режим «только чтение» (новый стиль `.uris-store-mode-readonly`).
- **F3 — импорт бэкапа без секций refs/presets больше не затирает файлы** (`src/data-port.js`). Блок зеркалирования импорта в файловые стора читал восстановленную (после миграции — пустую) копию из настроек независимо от того, что нес бэкап: частичный бэкап (экспорт без настроек, чужая вариация) заменял `uris_refs.json`/`uris_presets.json` пустыми массивами. Теперь replace вызывается только если бэкап реально несёт секцию (`Object.hasOwn(incomingShared, …)`); явный пустой массив по-прежнему импортируется как пустой набор. Rollback расширен: снапшот перед импортом захватывает живые refs/presets из файловых сторов и восстанавливает их при откате (раньше откат заканчивался наполовину — настройки возвращались, файлы оставались импортными).
- **F4 — разовый сбой пробы при старте больше не прикалывает сессию к настройкам** (`src/file-store.js`). Раньше `ready()` мемоизировал legacy-даунгрейд навсегда: сбой пробы на 5 секунд → все записи сессии шли в `settings.json`, а в следующей нормальной сессии молча отбрасывались как «orphans». Теперь `probe-error` ретраится (троттл 10 с, 404 эндпоинта — по-прежнему постоянный), а при переходе legacy→file записи, сделанные в legacy-сессии, объединяются с файловым состоянием union-by-id (файл выигрывает конфликты) и персистятся **до** стрипа копии — тот же порядок «сначала durable, потом удаляем». Union применяется только к сторам со `stripLegacyOnLoad` (галерея/референсы/пресеты); шаблоны со своей постоянной копией не сливаются. Orphans вне ретрая (неудавшийся strip) теперь дают тост для strip-сторов.
- **F5 — мелочи**: `countEntries` больше не клонирует всё зеркало на каждую запись (structuredClone ~12 мс на 713 карточках зря); `flushOnUnload` помечает payload отправленным до keepalive-запроса — `visibilitychange` + `pagehide` больше не шлют один и тот же payload дважды.

## 2026-09-12 — v0.8.6: данные вынесены из `settings.json` в серверные файлы

- **Правило размещения** (по вопросу «если эти данные потерять — что произойдёт?»): настройки → `extensionSettings`; работа пользователя → серверный файл через user-files API; восстановимое → localforage; привязанное к чату → `chatMetadata`.

- **Миграция безопасна**: сначала запись файла → ожидание подтверждения → только потом удаление копии из настроек. При обрыве копия остаётся и миграция повторяется на следующем запуске. ## 2026-09-08 — v0.8.6: оптимизация референсов v3 — webp исключён из провайдер-пути

- **Причина**: релей-апстримы за OpenAI-совместимыми шлюзами (adobe2banana, инцидент 2026-09-08) отклоняют webp на контент-валидаторе («Image edit file content does not match its declared MIME type», HTTP 400), хотя браузер кодирует корректно; исходный webp-файл мог уйти на провод через source pass-through.
- **Решение**: `OPTIMIZATION_VERSION = 'ref-v3-1024'`; канонические форматы — jpeg (opaque) / png (alpha); webp убран и из `CANONICAL_MIMES`, так что source pass-through больше не пропустит webp-оригинал. `options.formats` позволяет вызову явно закрепить набор: миниатюры галереи пинят webp (`native-image-storage.js`) — они локальные (URIS_Thumbs не сканируется в галерею) и до провайдеров не доходят. Инструментация `[refs] optimize: …` пишет в лог, какой формат реально ушёл на провод и почему (до подтверждения фикса инцидента).
- **Тесты**: `tests/references.test.js` — v3-каскад (jpeg/png по альфе, formats-пин, source pass-through без webp).

## 2026-09-08 — v0.8.6: API-ключ больше не стирается автоматически при правке коннекта

- **Симптом**: после неудачного запроса генерации ключ пропадал из коннекта — поле «Ключ» в карточке пустое, следующая генерация падала с `MISSING_API_KEY`.
- **Причина**: fingerprint-guard в `connection-store.js` — `updateConnection` сравнивал отпечаток `{endpoint, provider(=apiFamily)}` до/после и при расхождении молча вызывал `clearConnectionApiKey`. `apiFamily` — производное нормализатором поле (route contract / пин диалекта), поэтому клик «Попробовать …» в панели референсов — штатное восстановление после отклонения референсов (tab-generate.js) — или смена «Протокол» в карточке меняли отпечаток и стирали ключ. Смена endpoint стирала by design (запись 2026-09-05).
- **Решение** (сознательное: ключ не должен исчезать вообще): guard снят целиком, включая запись fingerprint-meta. Ключ привязан к id коннекта, а не к endpoint/протоколу; сценарий «ключ не должен уехать на чужой шлюз» для копий уже решён дизайном клонирования (ключ не копируется, вводится заново). Ключ покидает хранилище только явными действиями: удаление коннекта или сохранение пустого поля «Ключ». Протухший ключ на переправленном endpoint даст видимую 401 — восстановимо, в отличие от молчаливой потери.
- **Legacy**: `uris_api_key:<id>:meta` записи старых сборок больше не пишутся/не читаются; подчищаются при следующей записи/очистке ключа и при удалении коннекта.
- **Тесты**: `tests/connection-store.test.js` — «updateConnection never erases the browser-local key» (смена диалекта / evidence write-back / смена endpoint), «the key leaves storage only through explicit actions» (пустое поле, deleteConnection), проверка очистки legacy-meta. Полный набор зелёный (1036).

UTF-8-safe base64 (инструкции с кириллицей).
- **Настоящий flush на выгрузку** (`index.js`): `pagehide` + `visibilitychange→hidden` вызывают `flushTemplateWritesOnUnload()` — догоняющий `fetch(..., keepalive: true)` с последним незаписанным payload (лимит ~60 КБ, идемпотентно: это та же полная атомарная запись). Прежний `flushSettings()` оставлен, но он лишь перезапускает debounced ST — на settings больше ничего критичного не завязано.
- **Миграция и фолбэк**: при первой загрузке файла нет → зеркало seed'ится из settings-копии и заливается на сервер (копия в settings сохраняется для даунгрейда/бэкапов); битый/чужоверсионный файл → warn + повторная миграция из settings; user-files эндпоинт недоступен (старый ST, Node-тесты) → режим `legacy`, CRUD работает по settings как раньше (детект одним POST /api/files/verify). Режим резолвится один раз за сессию.
- **Починен баг индекса кэша** (`saveTemplate`): индекс искался в отфильтрованном `listTemplates()` (без неподдерживаемых legacy-записей), а писался в сырой `cachedTemplates` — при наличии legacy-записей затирался чужой слот кэша и появлялся дубль (хранилище оставалось корректным, лечилось перезагрузкой). Теперь поиск по `id` прямо в `cachedTemplates`; CRUD в file-режиме дополнительно работает на клонах — кэш и mirror больше не делят ссылки.

В legacy-режиме все три пути — no-op, поведение прежнее.
