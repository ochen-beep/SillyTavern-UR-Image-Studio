## Контекст и охват

Сверка визуального слоя расширения (`style.css` + `src/ui/*`) с документацией
SillyTavern, WCAG и спеками проекта первоначально выявила шесть кандидатов на

логика пайплайна НЕ затрагиваются.

Документ написан в «блочном» стиле проекта (`Контекст / Проблема / Решение /

## Цели

- Восстановить потерянную при рефайнде `mode → model` визуальную рамку ручного режима.
- Убрать мёртвый артефакт `innerHTML` на `<input>` (legacy host).
- Починить выбор референса из галереи: кастомные кнопки popup должны корректно
  возвращать индекс по контракту ST `POPUP_RESULT.CUSTOM1..CUSTOM9`.
- Убрать ререндер всей mobile-screen при вводе в поиск (drop caret → UX-баг).
- Дать имя осознанному 480-порогу mobile-стека референсов с объясняющим комментарием
  (избавиться от немотивированной магии, не меняя самого порога — см. N2).

## Не-цели (явно)

- Не переписываем picker-overlay на нативный `<dialog>` (focus trap не критичен для пет-проекта).
- Не чистим мёртвый CSS кластер (descref/proxy/host-table) — отдельная косметика.
- Не переводим `<div onclick>` на `<button>` mass-migration — значение `should`, не `must`, делается отдельным проходом.
- Не трогаем дизайн-токены, палитру Figma, `@supports`-фолбэки, `showRefPicker`-обёртку через `getContext()` (всё осознано и подтверждено спекой).
- Не трогаем `refs-library.js`, провайдеры, пайплайн.

## Блок N1: контракт popup в `showRefPicker` (делается первым)

### Проблема

`tab-gallery.js:205` формирует кастомные кнопки как объекты **без `result`**:
```js
const customButtons = refs.map(r => ({ text: r.name || '?' }));
```
Согласно контракту ST (`public/scripts/popup.js`, ветка `release`,
верифицировано через `getContext().POPUP_RESULT`):

- Для массива **строк** фреймворк авто-присваивает `result: index + 2`
  (диапазон 2..N, НЕ в `CUSTOM1..9`).
- Для объектов `{...}` без `result` — авто-присваивания НЕТ:
  `buttonElement.dataset.result = String(undefined)`. При клике
  `Number("undefined") = NaN` → выбрасывается `Invalid result control`;
  по Enter возвращается `defaultResult = POPUP_RESULT.AFFIRMATIVE`.

Таким образом `res >= POPUP_RESULT.CUSTOM1` (1001) на `:213-214` либо
никогда не срабатывает (клик бросает), либо ловит только Enter —
который дает `AFFIRMATIVE` (1), не попадающий в диапазон. Итог: выбор
референса тихо возвращает `null`, идиоматический контракт не соблюдён.
Идиоматичный паттерн из ядра ST (`chats.js:989`) — **явно** проставлять
`result: POPUP_RESULT.CUSTOM1..n` на каждой кастомной кнопке и сравнивать
поимённо.

### Решение

Кнопкам проставляется `result` из `ctx.POPUP_RESULT.CUSTOM1..CUSTOM9`
(число кнопок ≤ 9, иначе деградация на `Popup.show.input` — см. альтернативу B).
Сравнение переписывается на поимённый `switch` по `ctx.POPUP_RESULT.CUSTOMn`,
вариант-CUSTOM-CONST-many или простой `if (res === CUSTOM1) return refs[0].id`
карта по зарегистрированным кнопкам. Это снимает и исходную suspicion
«фрагильное index-math», потому что мы перестаём полагаться на
contiguous-1001-допущение — сравниваем поимённо.

Лимит: если `refs.length > 9`, кастомных кнопок будет больше, чем есть
констант; тогда путь деградирует на возврат `null` с тостом
(существующее поведение вне диапазона), явное ограничение спеки.

### Альтернативы

- **A. Оставить как есть, «работает же».** Отвергнуто: верификация контрактом
  показывает, что НЕ работает корректно — это кандидат на «молча сломано».
- **B. Использовать `Popup.show.input` со списком чисел** вместо кастомных
  кнопок. Отвергнуто: теряет визуальную «кнопка на референс» модель, которая
  тут семантически важна (пользователь жмёт имя, а не вводит число).
- **C. Динамический base `100 + index`** как `personas.js` (обходит
  `CUSTOM1..9`). Отвергнуто: вводит магический base вне enum, что ~более
  хрупко, чем поимённое использование публичного контракта.

Поимённый `CUSTOMn` — единственный путь, использующий задокументированный
контракт (`chats.js` — reference usage) и не выдумывающий свой base.

### Проверка

- Открыть «Генерация» → выбрать пост с картинкой → «Сохранить в референсы»
  (или picker замены) → убедиться, что клик по имени референса действительно
  выбирает именно его (не отдаёт `null` и не мешает кнопкам).
- ≥9 кнопок: тост о превышении, без бросания исключения в ST popup.
- Enter на «Отмена» возвращает `null` (тост не показываем отмену как ошибку).

## Блок N2: порог mobile-стека референсов — переосмыслено, не баг

### Предположение в первом ревью

В первом code review JS-порог `480` (ширина **контейнера** вкладки, `root.clientWidth`)
при CSS-μ-media `@media (max-width: 768px)` (на `window`) был назван «рассинхрон-
багом»: между 481–768px CSS mobile, а JS «десктоп».

### Уточнение при сверке

Проверка кода и тестов `tab-references.test.js` показала, что разные оси —
**осознанное** решение, не баг:
- `uris-refs-mobile-stack` (вертикальный 3-экранный стек референсов) ставится
  **классом из JS по `root.clientWidth`**, а не CSS media. Это сделано потому,
  что `#urisBody` уже живёт внутри фиксированного плавающего окна шириной
  ≤460px (`style.css:.uris-window width:460px`); CSS media на `window` ведёт
  другие правила (`.uris-gallery-grid` 2-колонки, lightbox, `.uris-tabs`), и
  жёстко сцеплять JS-порог с window-μ было бы некорректно.
- Тест `tab-references.test.js:48` фиксирует контракт явно: «Set clientWidth
  > 480 so it's desktop mode» + `clientWidth: 600` ожидает sidebar/grid.
  Сведение к 768 ломает этот валидный 600px-«десктоп»-тест (что и подтвердилось
  при первой попытке реализации — 8 фейлов в этом файле).

Таким образом 480 — это **тестируемый контракт проекта**, а не магическое число.

### Решение

Порог 480 **сохранён**, но вынесен в именованную константу
`REFS_MOBILE_BREAK = 480` в `tab-references.js` с объясняющим комментарием:
почему ось — контейнер, а не окно, и почему 480 осознанно. Все магические
вхождения `_cw < 480` (`render`, `_setupResize`) заменены на константу —
устранена «немотивированная магия», но не само значение. Это и есть фикс:
читаемость без поведенческой смены.

### Альтернативы (рассмотренные и отвергнутые при сверке)

- **A. Свести порог к 768 (как предлагалось в первом ревью).** Отвергнуто:
  ломает валидные 600px-десктоп-тесты; оси разные, сведение некорректно
  (это и было моим ошибочным предположением в первом ревью).
- **B. `isMobileViewport()` из `window.js`.** Отвергнуто: оно меряет окно, а
  переключение завязано на `root.clientWidth` — другая ось (то же, что A).
- **C. `matchMedia('(max-width: 768px)')` event-based.** Отвергнуто:
  ResizeObserver уже гоняет `_cw`; `matchMedia` redundant, ось снова window.
- **D. Динамически чтить CSS media через sentinel-элемент.** Отвергнуто:
  over-engineering, общий порога достаточно.

### Проверка

- `grep "_cw < 480"` в `tab-references.js` → 0 вхождений (только в комментарии
  как историческая ссылка); все пути идут через `REFS_MOBILE_BREAK`.
- Тесты `tab-references.test.js` проходят зелёно (40/40 при полной сводной
  свёрке; 757/757 в полном прогоне — см. конец спеки).
- Поведение 600px-«десктопа» сохранено: JS даёт sidebar/grid, как в тесте.

## Блок N3: потерянная рамка ручного режима (`mode` ↔ `model`)

### Проблема

Рефайнд переименовал класс `uris-server-manual-mode` (контейнер пунктирной рамки,
`style.css:258, :264`) → `uris-server-manual-model` (input Model ID,
`server-connection-form.js:143, :159`). CSS ждёт контейнер `-mode` и стилизует
пунктирную обёртку с `.uris-row { margin-bottom: 0 }`; в реальности класс
висит на `<input>`, контейнер ничего не получает → рамка потеряна. Спеки под
это переименование нет — регресс рефактора.

### Решение

Привести к единому имени. Что оставить:
- Логически класс стилизует **режим** (manual entry mode), и `.uris-server-manual-mode`
  носящий контейнер с `.uris-row` override осмысленнее. Поэтому правится
  разметка: оборачивающий div получает класс `uris-server-manual-mode`,
  а input/поля внутри сохраняют свои классы (`uris-server-manual-model` остаётся
  хуком для чтения значения через `value('.uris-server-manual-model')`).
- Уже есть контейнер `canManual`-блок; он и должен нести класс рамки.

Итог: разметка берёт `uris-server-manual-mode` на обёртку (восстановление
намерения CSS), ничего не меняя в логике чтения `manualModelId`.

### Альтернативы

- **A. переименовать CSS-правило под `-model`** и стилизовать input. Отвергнуто:
  теряется `.uris-row` override (рамка-контейнер семантически правильнее контейнера).

### Проверка

- Таб API → развернуть server-card → «ручной режим» при провале каталога:
  видна пунктирная рамка вокруг строки «ID модели», как до рефайнда.

## Блок N4: мёртвый `innerHTML` на `<input>` (legacy host)

### Проблема

`tab-generate.js:333` — `<input type="hidden" id="urisRefsModeBadge">` +
`:776-777`: `const badge = root.querySelector('#urisRefsModeBadge'); if (badge)
badge.innerHTML = '';`. `<input>` не имеет `innerHTML` — это no-op, мёртвый

(`:334`) остаётся осмысленным — его `renderCap` (`:894`) пишет `cap.textContent`
(работающая ветка), не трогать.

### Решение

Удалить `<input type="hidden" id="urisRefsModeBadge">` из разметки (`:333`)
и мёртвый блок `badge`/`innerHTML=''` (`:776-777`). `#urisRefsCap` и
`renderCap` оставить как есть (working fallback).

### Альтернативы

- **A. Перевести на `<div hidden>` с innerHTML.** Отвергнуто: badge удалён по
  спеке, реанимировать его не нужно — это просто зачистка.

### Проверка

- Tаб «Генерация»: панель референсов, cap-indicator и Stage 2-строка работают
  как прежде (renderCap пишет текст в #urisRefsCap); баг с innerHTML-on-input
  больше не загрязняет код.

## Блок N5: `value=` на `<select>` — переосмыслено, не баг (mock-контракт)

### Предположение в первом ревью

`server-connection-form.js` ставит `value="..."` на `<select ...-api-family>`
(строка `<select class="..."> value="${escapeHtml(...)}"`) и на `<select ...-route>`.
Был назван «невалидным/мёртвым» атрибутом, т.к. HTML-стандарт не определяет
`value=` на `<select>` (браузер берёт `.value` из `<option selected>`).

### Уточнение при сверке

Проверка тестов `tab-api-server-connections.test.js` показала, что в проекте
`tests/fake-dom.js` **не реализует** `HTMLSelectElement.value` из `<option selected>`:
`fake-dom` хранит `node.value` обычным свойством, которое выставляется
атрибутом `value="..."` в `parseHTML` (строка `if (k === 'value') node.value = v`).
Без `value=`-атрибута `select.value` в fake-dom остаётся пустым → тесты вида
`assert.equal(form.querySelector('.uris-server-route').value, route.id)` фейлят
(подтверждено эмпирически при первой попытке снять — 4 фейла в
`tab-api-server-connections.test.js`).

Таким образом `value=` на `<select>` НЕ вредный артефакт, а **фактический
workaround ради fake-dom** — ровно тот же приём, что и дублирование custom выборов
через `<option selected>`. Дублирование намеренное: рендерит и `value=`, и
`selected`, и option — гарантия совпадения в обоих средах, и any drift ломает одну
из них (либо браузер, либо mock). Это не «очевидный костыль в коде», а трейд-офф
тест-инфраструктуры, адекватный пет-проекту.

### Решение

`value=` на `<select>` **сохранён**. Спека N5 закрывается без правок: первый code
review переинтерпретировал mock-compat-приём в «мёртвый код». Никаких изменений
в `server-connection-form.js` не делается. (Альтернатива — расширять fake-dom
реализацией `HTMLSelectElement.value` по selected option — отвергнута: она
меняет shared mock, использует många тест-зависимости и ради косметики
недопустима для пет-проекта.)

### Проверка

- `tab-api-server-connections.test.js` зелёный (4 теста, проверяющие
  `select.value === 'auto'`/`route.id`, проходят).
- Полный прогон `node --test tests/*.test.js` — 757/757 (см. конец спеки).
- В реальном браузере `<option selected>` корректно выставляет `select.value`
  вне зависимости от `value=`-атрибута (он просто игнорируется мотором); риск
  «расхождения» в проде отсутствует, т.к. разметка рендерит оба.

## Блок N6: ререндер mobile-search на каждый символ

### Проблема

`tab-references.js:391` `_renderMobileGrid(root)` при вводе в поиск
перерисовывает **всю** mobile-grid секцию через `host.innerHTML = ...`,
включая сам `<input class="uris-mobile-search">`. Каретка в поиске падает
после каждого символа → нельзя набрать строку (`:444` триггерinput handler).

### Решение

Разделить: при вводе в поиск обновлять только **результат-список**
(`_renderMobileGridInner`/контейнер карточек), а не всю `_renderMobileGrid`
с input. Поиск рендерится один раз; последующие keystroke только перерисовывают
контейнер ниже `<input>`, сохраняя фокус и caret.

Практически: вынести input вне `innerHTML`-перерисовки (или мемоизировать его
состояние), перерисовывать только контейнер с карточками.

### Альтернативы

- **A. Восстановить caret программно (save/restore selection range).**
  Отвергнуто: патч симптом, всё равно теряет scroll; правильнее не разрушать input.
- **B. Debounce ввода.** Снижает частоту потерь caret, но не устраняет сам баг.
  Отвергнуто как half-measure.

### Проверка

- Мобильный вид → вкладка «Референсы» → поиск: набрать «abc» без потери
  каретки; фильтр реагирует; скролл в результате не сбрасывается при наборе.
