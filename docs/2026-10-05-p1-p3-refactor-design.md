## 0. Инварианты (не нарушаются ни одним пунктом)

Эти свойства — фундамент, проверенный живыми генерациями. Любое изменение, которое им противоречит,
авто-отклоняется независимо от красоты решения:

1. **Платный POST не повторяется автоматически**, пока не доказано (OPTIONS-оракул), что исходный
   запрос не покинул браузер. Источник: `image-transport.js` (preflight oracle), инциденты
   2026-09-28.
2. **Контракт выбирается только из маршрута** (`route.generationContract`), никогда — по имени
   модели, хосту или регэкспу (`image-provider-registry.js`).
3. **Журнал диагностики однострочен и grep-аем**, пишется всегда, читается только человеком
   (`capability-observer.js`, `diagnostic-events.js`). Пункт 2.6 меняет это — см. там.
4. **Секреты не персистятся**: `stripSecrets` на границе записи, ключи — только в браузер-локальном
   хранилище (`connection-store.js`).
5. **Совместимость данных**: существующие записи `uris_delivery_evidence`,
   `uris_edit_dialect_evidence` (localforage) и `connections` (серверные настройки) читаются без
   миграционных скриптов; новые поля — опциональные.
6. **Один диалект на попытку, память о выигрышном диалекте — TTL 30 мин** (`delivery-evidence.js`).

## 1. P1 — поведение, которое бьёт по пользователю сейчас

### 1.1. Слет параметров генерации при перерендере вкладок

**Симптом (воспроизведён дважды в живой сессии 2026-10-04).** Пользователь выставляет
Стороны=2:3 / Quality=high на вкладке «Генерация», переключается на «API» (смена активной карточки)
или панель перерисовывается после перестройки промпта — селекты возвращаются к прежним значениям
черновика. Два платных прогона в логах ушли с `aspectRatio: "16:9"` вместо выставленного `2:3`
(`dispatch-start` 23:55:28 и 23:59:39, conn nano-gpt). Пользователь ничего не замечает до
результата.

**Текущее поведение.** Селекты `#urisAspect/#urisImgSize/#urisQuality` рендерятся в
`tab-generate.js` из значений черновика (`generation-drafts.js`, ключ — чат+пост). Обработчик
`change` обновляет состояние, но сохранение черновика и/или перерендер панели после `onSaved`
(смена активной карточки в `tab-api.js` → `onSaved` → полная перерисовка вкладок) читает
**перезаписанный/старый** вариант черновика. Воспроизводимый путь: смена активной карточки в
момент несинхронизированного черновика.

**Целевое поведение.** Любое изменение селекта параметров синхронно и атомарно попадает в
персистентный черновик ДО любого возможного перерендера; перерендер всегда восстанавливает UI из
последнего известного значения, а не из повторно загруженной записи.

**Изменения:**
- `src/generation-drafts.js`: убедиться, что апдейт параметров из `tab-generate.js` пишется
  синхронно в память и в отложенную персистенцию (без гонки с перерендером). Если черновик
  перечитывается с сервера на `onSaved` — мержить, а не замещать поле `params`.
- `src/ui/tab-generate.js`: при ре-рендере брать параметры из «живого» in-memory черновика;
  при расхождении UI↔черновик — приоритет у UI (обратный мерж), не у перечитанной записи.

**Критерии приёмки:**
- Тест (node --test, `fake-dom.js`): выставить 2:3 → сменив активную карточку, вызвать
  перерендер панели → `#urisAspect.value === '2:3'`, черновик содержит 2:3.
- Живой smoke: выставить 2:3/high → сменить карточку → сгенерировать → `dispatch-start.details`
  содержит `aspectRatio: "2:3"`, `quality: "high"`.

**Риски:** низкие; касается только UI-слоя. Контрактные тесты адаптеров не затрагиваются.

### 1.2. Варнинг на молчаливый даунгрейд разрешения

**Симптом.** Запрос `imageSize: "4K"` к nano-gpt `nano-banana-pro` (2026-10-05 01:01 UTC) вернул
1024×1024 (1 МП). В журнале **ноль** `provider-warnings`: аспект совпал (1:1), существующий
пост-чек видит только пропорции. Провайдер молча уронил тир — пользователь платит за 4K, получает 1K.

**Текущее поведение.** `image-api.js` после материализации считает `aspectDeviates(...)` и пишет
`aspect-mismatch` + предупреждение. Разрешение не проверяется вовсе.

**Целевое поведение.** Тот же пост-фактум блок проверяет ожидаемый минимум пикселей для запрошенного
тира; недобор — предупреждение пользователю + диагностическое событие `resolution-shortfall`.

**Пороговые значения (эмпирически по фактическим выдачам этой сессии):**

| Запрошен | Ожидаемый минимум площади | Основание |
|---|---|---|
| 1K | ≥ 0.80 МП | фактические 1K-выдачи: 1024×1536=1.57, 1280×720=0.92 |
| 2K | ≥ 2.0 МП | фактические 2K-выдачи: 2752×1536=4.23 |
| 4K | ≥ 6.0 МП | консервативно: реальные 4K-слоты ≈ 16 МП, квота на ложные срабатывания |

**Изменения:**
- `src/image-api.js`: рядом с блоком `aspectDeviates` — `resolutionShortfall(width, height, imageSize)`
  (вынести функцию в `src/image-dimensions.js` для юнит-теста); недобор → `result.warnings.push(...)`
  + `recordDiagnosticEvent({ event: 'resolution-shortfall', ... })`.
- Варнинг НЕ возникает, если тир не поддерживался моделью и был опущен (об этом уже сказал
  `provider-warnings` от адаптера) — читать фактический факт «параметр ушёл на провод» из
  `diagnosticRequestOptions.wireFields` недёшево; допускается эвристика: не варить, если в этом
  запросе уже есть `provider-warnings` с `feature: "Размер"`.

**Критерии приёмки:**
- Юнит-тест `image-dimensions.test.js`: таблица порогов, случаи «4K запрос → 1 МП → warn»,
  «2K запрос → 4.2 МП → нет», «1K запрос → 0.92 МП → нет».
- Контрактный тест: у `generateImageRequest` при shortfall в `result.warnings` появляется запись с
  `feature: "Размер"`.

### 1.3. Лаг записи журнала диагностики (write-behind до ~2 минут)

**Симптом.** События `dispatch-*` появляются в localforage `uris_event_log` с задержкой до 1–2 минут
после того, как генерация уже идёт/завершилась. В живой сессии это привело к трём повторным запускам
(дублирование оплаты). Также ломает любые внешние наблюдатели (тестовая автоматизация, дампы по
запросу пользователя).

**Текущее поведение (уточнено сверкой).** Персистенция уже есть: дебаунс 500 мс (`PERSIST_DELAY_MS`,
`schedulePersist` на каждой записи) и flush на `visibilitychange → hidden` (index.js, вместе с
остальными store-flush). Дыра в другом: чистый дебаунс голодает при потоке событий, а в фоновой
вкладке Chrome троттлит таймеры до ~1/мин — события, записанные уже после ухода со вкладки
(dispatch-response, materialize, gallery-write приходят через десятки секунд работы генерации),
ждут отложенный флаш минутами. Принудительного флаша на stage2-end/error нет.
`MAX_DIAGNOSTIC_EVENTS = 1000`.

**Целевое поведение.** Событие попадает в персистенцию ≤ 5 с после `recordDiagnosticEvent`;
флаш форсируется на `stage2-end`/`stage2-error` и на `visibilitychange → hidden` (этот уже есть —
не дублировать). Таймер 5 с — **throttle** (максимальный возраст несохранённых событий), а не второй
дебаунс: быстрый `PERSIST_DELAY_MS`-путь остаётся, throttle-таймер взводится один раз на первое грязное
событие и НЕ сбрасывается последующими записями. Батч-запись сохраняется (один `setItem` на флаш).

**Изменения:**
- `src/diagnostic-events.js`: dirty-флаг + несбрасываемый `setTimeout(flush, 5000)` от первой
  несохранённой записи; `flushDiagnosticEvents()` на stage2-end/error (вызвать из `image-api.js`
  finally).
- Гарантия порядка: флаш пишет весь массив целиком (как сейчас) — конкуренция не добавляется.

**Критерии приёмки:**
- Тест: `recordDiagnosticEvent` → (виртуальный таймер +5с) → `lf.getItem('uris_event_log')` содержит
  событие.
- Живой smoke: после генерации событие `dispatch-start` читается из localforage через ≤ 5 с.

**Риски:** запись чаще — на слабых дисках удлинит флаш; смягчается батчингом (уже есть).

### 1.4. `extractErrorDetail` не читает top-level `message`

**Симптом.** Nano-gpt отвечает на 400 телом `{"message":"Invalid request parameters. Please check
your input and try again.","code":"request_error"}` (подтверждено curl и нетдампом 2026-10-05).
URIS показывает «HTTP 400» без причины — `extractErrorDetail` знает только `error.message` и
`error` (строка).

**Целевое поведение.** Порядок извлечения: `error.message` → `error` (строка) → **`message`**
(строка, top-level) → `detail` / `error.details` (опционально). Усечение до 240 символов — как
сейчас на месте вызова.

**Изменения:**
- `src/providers/image-base.js` `extractErrorDetail(payload)`: добавить ветку
  `typeof payload?.message === 'string' ? payload.message : ''` третьим приоритетом.
- Эффект мгновенный на всех контрактах: raw-лог и панель ошибок станут содержательными для
  nano-gpt и любых шлюзов с тем же форматом.

**Критерии приёмки:**
- `tests/image-base-read-json-response.test.js`: кейсы `{"error":{"message":...}}` (как раньше),
  `{"error":"..."}` (как раньше), `{"message":"..."}` (новый), `{"message":{...}}` (объект —
  игнор), HTML-тело (пусто).

## 2. P2 — структурные упрощения

### 2.1. Единая память о доставке (вместо трёх)

**Проблема.** Факт «прямая доставка к этому шлюзу работает?» хранится в трёх независимых местах:

1. `proxy.js` `_hostStrategy` (Map host→'direct'|'proxy') — пишет `autoFetch` (скачивания,
   каталоги, идемпотентные GET) и `probeDeliveryStrategy`.
2. `delivery-evidence.js` — персистентные факты платных POST (directOkAt/directBrokenAt, TTL
   30 мин/24 ч), читаются лестницей «Авто» в `image-api.browserDeliveryRoute`.
3. `connection.detected.delivery` — вердикт кнопки «Проверить» (`connect-probe.js`), тоже читается
   лестницей как fallback.

Приоритеты между (2) и (3) зашиты в `browserDeliveryRoute` («свежий успех прямой перекрывает
устаревший вердикт пробы») — это нетривиальная логика поверх двух источников. Живая сессия
подтвердила работоспособность, но три писца одного факта — гарантированный источник рассинхрона
(уже сейчас `autoFetch` флипает хост на 'proxy' после ambiguous, а лестница об этом не знает, и
наоборот).

**Целевое поведение.** Один модуль фактов доставки — `delivery-evidence.js` расширяется до
единственного источника для **платных POST и лестницы «Авто»**:

```
record = { host, probe: { at, verdict: 'direct'|'proxy' } | null,
           directOkAt: iso|null, directBrokenAt: iso|null }
API:  hintFor(conn, now) → 'proxy'|'direct'|null        // приоритет: broken < TTL → proxy;
                                                      // ok < 24ч → direct; иначе probe; иначе null
      notePostOutcome({connId, endpoint, delivery, ok})
      noteProbe({connId, endpoint, verdict})            // пишет и probe-вердикт
      notePreflightDead(connId, endpoint)
      clearFor(connId)
```

- `connect-probe.js` после пробы каталога пишет `noteProbe` вместо (или вместе с)
  `detected.delivery`; `detected.delivery` остаётся **только для отображения** на карточке.
- `image-api.probeDeliveryBeforeFirstPost` удаляется как дубликат: его работу выполняет
  `noteProbe` из общего кода пробы.
- `_hostStrategy` в `proxy.js` **остаётся**, но только как сессионный кэш для идемпотентных GET
  (скачивания/каталоги); платные POST его не читают и не пишут (сейчас `autoFetch` флипает хост
  и на платных — убрать этот путь: платные POST в `autoFetch` не заходят по факту, проверить
  тестом).

**Миграция:** существующие записи `uris_delivery_evidence` валидны как есть (схема та же +
опциональное поле `probe`). Записи без `probe` ведут себя как сегодня.

**Границы пункта (уточнено сверкой).**
- Текстовый путь НЕ мигрирует: `providers/openai.js` и `providers/gemini.js` шлют платные
  chat/completions POST через `autoFetch` (он пишет `_hostStrategy` и уже имеет noResubmit-guard).
  В этом цикле они остаются как есть; «GET-only» для `_hostStrategy` касается только диспетча
  картинокного пути.
- `image-api.probeDeliveryBeforeFirstPost` не удаляется, а **переписывается на `noteProbe`**:
  его защита (бесплатный GET /models до первого платного POST на непроверенном коннекте) — реальное
  поведение; удаление означало бы первый POST вслепую для тех, кто ни разу не жал «Проверить».

**Критерии приёмки:**
- `delivery-evidence.test.js`: приоритеты hint'а (broken→proxy, ok→direct, probe→по вердикту,
  пусто→null), TTL-границы, host-mismatch → null.
- Контрактный тест: `browserDeliveryRoute` читает ТОЛЬКО `delivery-evidence` (grep-тест: в
  `image-api.js` нет обращений к `_hostStrategy`/`detected.delivery` для платных POST).
- Живой smoke: убить прямую доставку (шлюз без CORS) → первая генерация ambiguous → вторая
  через прокси без повторного прямого стука.

### 2.2. Транспорт возвращает факт доставки; журнал снова write-only

**Проблема.** `image-api.js` (блок `finally`, ~строка 266) определяет «уехала ли попытка через
прокси» **поиском по журналу**: `listDiagnosticEvents().some(e => e.event === 'dispatch-fallback' &&
e.requestId === ...)`. Управляющее решение опирается на write-behind буфер (см. 1.3) и глобальный
список — недетерминизм и скрытая связность.

**Целевое поведение.** `fetchImageRoute` (и обёртки `requestJson/requestMultipart`) помечает
возвращаемый `Response` несчётным полем `__urisAttempt = { initialDelivery, finalDelivery,
rescuedBy: 'preflight-oracle'|null, attempts: n }`. Обёртка транспорта в реестре переносит штамп
на `invocation.request.delivery`; `image-api.js` читает его в `finally`; журнал с этого момента
никем не читается.

**Изменения:**
- Сверка: `invocation.response` **не существует** — адаптеры возвращают уже разобранный
  `{kind, value, warnings}`, Response до `image-api.js` не доходит. Поэтому реализация — обёртка
  транспорта в `image-provider-registry.js` (`invokeImageProvider` подставляет `defaultTransport`,
  когда транспорт не инжектирован): обёртка читает `response.__urisAttempt.finalDelivery` и ставит
  штамп на `invocation.request.delivery` (механика штампов уже зеркалится в finally,
  `image-api.js:260-268`) — ноль правок в семи адаптерах. Тесты, инжектирующие собственный
  транспорт, ведут себя как раньше.
- `src/image-transport.js`: во всех трёх путях возврата (proxy-first, direct, rescue) ставить
  `__urisAttempt` через `Object.defineProperty` (enumerable: false, try/catch для тестовых
  двойников Response).
- `src/image-api.js`: `finally` читает штамп `invocation.request.delivery`; поиск по
  `listDiagnosticEvents()` удаляется.

**Критерии приёмки:**
- `image-transport.test.js`: каждый путь доставки ставит корректный `finalDelivery`
  (proxy-first → 'proxy'; direct → 'direct'; rescue → 'proxy' + `rescuedBy`).
- Grep-тест: `listDiagnosticEvents` не импортируется в `image-api.js`.

**Риски:** Response из тестовых стабилей без `clone` — свойство ставить через defineProperty с
try/catch; при отсутствии — поведение как сегодня (fallback на журнал не возвращать, достаточно
`{ finalDelivery: 'unknown' }`).

### 2.3. `provider-descriptors.js`: метаданные всех 7 контрактов

**Проблема.** Дескрипторы есть только у pollinations/naistera/comfyui. У остальных четырёх
контрактов та же информация размазана по адаптерам:

- нормализация endpoint'а — **5 реализаций**: `endpointBase` (дописывает `/v1`),
  `comfyBase` (отрезает `/api`), `baseUrl` naistera (отрезает `/api`), pollinations `generationUrl`
  (отрезает `/v1`), openrouter `base` (требует `/api/v1`);
- словари параметров и авторизация повторяются в `requireInvocation` (регэксп
  `/pollinations|naistera/` — прямое нарушение инварианта №2 по духу).

**Целевое поведение.** Каждый дескриптор получает:

```
endpoint:  { normalize(input) → canonical, generationPath, editPath?, modelsPath? }
auth:      { required, scheme, tokenPrefix|null, validatorId? }
polling?:  { intervalMs, maxMs }
wire:      { aspectTable?: 'gpt'|'dalle'|'comfy', qualityValues?: [...] }
```

- `src/endpoint-utils.js` (новый): `resolveEndpoint(descriptor, rawEndpoint)` — единая функция;
  адаптеры вызывают её вместо своих нормализаторов.
- Сверка масштаба: нормализаторов не 5, а **~10** — помимо адаптерских есть свои билдеры в
  `catalog.js` (`versionedUrl`, `pollinationsUrl`, `naisteraUrl`, `buildNanoGptImageModelsUrl`)
  и `nativeModelsUrl` в `connect-probe.js`. `endpoint-utils.js` обязан покрыть и их, иначе каталог
  и генерация разойдутся в нормализации одного endpoint'а.
- Токен-требования pollinations/naistera дублированы в **трёх** местах (`requireInvocation`,
  `generateImageRequest`, валидаторы адаптеров) — сводятся к `descriptor.auth` во всех трёх.
- Осторожно: `isBearerContract` (image-base.js:319) матчит **display name** провайдера, не контракт;
  замена на дескриптор требует прокинуть контракт в `readJsonResponse` (сигнатура меняется во всех
  адаптерах) — заложить в оценку шага 6.
- `requireInvocation` валидирует ключ по `descriptor.auth`, регэксп удаляется.
- Тела запросов/парсеры ответов адаптеров **не трогаются** — рефакторинг только про URL/мету.

**Критерии приёмки:**
- Существующие `image-provider-adapters.test.js` проходят БЕЗ изменений URL-ов в ожиданиях

## 3. P3 — продуктовые улучшения (по наблюдениям логов)

### 3.1. Факт-строка карточки: «модель/шлюз отвечает ошибкой»

Живьём найдено 6 мёртвых записей каталогов (dall-e-3 → 400, gpt-4o-image → 410,
imagen-3.0 → 400 на nano-gpt; flash-lite → 404 на apiddt; gpt-image-1.5 → 400 на elysium;
flash-image-preview → 200-без-картинки на linkapi). Каталоги устаревают тихо.

**Целевое поведение.** `capability-observer.js` уже классифицирует исходы. Добавить сессионный
счётчик (in-memory, без новой персистенции) исходов per (connId, modelId): ≥ 2 подряд
`provider-error`/`missing-image` → в факт-строке карточки бейдж «последние N генераций модели X
упали (HTTP …)». Сбрасывается первым успехом и кнопкой «Проверить».

### 3.2. Guard от двойного запуска

Двойной клик «Сгенерировать» = повторная оплата (в этой сессии 3–4 задвоенных прогона; QUEUE
серилизует, но не глушит дубли). **Целевое:** при enqueue, если в очереди/исполнении уже есть
запись с тем же (connId, modelId, promptHash, aspect, size, quality) — тост «Такая генерация уже
в очереди — Запустить всё равно / Отмена» (кнопка «Всё равно» — явный обход). Реализация в
`pipeline-queue.js` / точке `stage2` submit; hash — FNV-1a 32 (не крипто, идемпотентность не нужна).

### 3.3. Маркер «шлюз не поддерживает редактирование» в факт-строке

Нетдамп: ddtnew `/v1/images/edits` → 400 всегда (шлюз не релеит edits); nano-gpt edits — только
через JSON+прокси; apihub edits — CORS-мёртв (28.09). Пользователь не может отличить «сломал
настройку» от «шлюз так не умеет». **Целевое:** после ≥ 2 неудачных edit-попыток разных диалектов
(факты уже есть в `editDialectEvidence`) факт-строка показывает «редактирование: шлюз отвечает
ошибкой на оба диалекта». Данные уже собраны — только рендер.
