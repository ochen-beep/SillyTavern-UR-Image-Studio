# Авто-доставка, которая учится: дизайн (2026-09-28)

## Проблема

«Доставка: Авто» для платного генерационного POST была синонимом «только напрямую»:
`browserDeliveryRoute` (image-api.js) выбирал прокси только по явной галочке
`overrides.delivery === 'proxy'`. Прямой POST, убитый CORS/сетом, бросал
`IMAGE_DELIVERY_AMBIGUOUS` и **не оставлял никаких следов**: следующая генерация
повторяла ту же гиблую попытку. Пользователю нужно было вручную идти в карточку,
ставить «Через прокси», возвращаться и перезапускать генерацию.

При этом README.md обещал обратное («the next attempt goes through the ST proxy») —
для текстового пути это правда (`autoFetch` флипает стратегию хоста), для
картиночного — нет. Расхождение документ ↔ код.

## Инвариант, который нельзя ломать

Платный POST не ретраится автоматически, пока не доказано, что первый запрос не
покинул браузер. CORS-фейл неотличим от «сервер обработал и ответ потерян»
(детали CORS недоступны JS). Повтор без доказательства = риск двойной оплаты.
Все `noRetry`-маркеры, `callWithRetry`, recovery-записи остаются нетронутыми.

## Решение: три слоя

### Слой 1 — лестница решения в `browserDeliveryRoute`

Порядок для JSON-маршрута (multipart всегда direct — прокси JSON-only):

1. `overrides.delivery === 'proxy'` → прокси (явный приказ).
2. `overrides.delivery === 'direct'` → напрямую (явный приказ, обучение игнорируется).
3. Иначе («Авто»): свежий опыт POST (`deliveryHintFor`) → прокси, если прямая
   ломалась < 30 мин; свежий прямой успех (< 24 ч) сильнее факта пробы;
   иначе факт пробы `detected.delivery === 'proxy'` → прокси;
   иначе напрямую. Синхронный кэш `isCorsProxyAvailable() === false`
   (прокси выключен в config.yaml) откатывает авто-решение на direct —
   лучше привычный ambiguous, чем гарантированная ошибка прокси.

Механика: `browserDeliveryRoute` штампует в `transport` новое поле
`deliveryPolicy: 'auto' | 'explicit-direct' | 'explicit-proxy'`. Без штампа
(маршруты из тестов/старых записей) транспорт считает политику
`explicit-direct` — поведение не меняется ни для кого, кроме явного «Авто».

### Слой 2 — опыт POST (`src/delivery-evidence.js`)

Персистентное per-connection знание `conn.deliveryEvidence`:
`{ host, directBrokenAt, directOkAt, ts }`.

- Прямой POST упал с `IMAGE_DELIVERY_AMBIGUOUS` → `directBrokenAt = сейчас`.
- Прямой POST успешен (любой HTTP-ответ) → флаги сброшены, `directOkAt = сейчас`.
- Прокси-успех знаний о прямой не меняет (самолечение по TTL остаётся).
- TTL сломанной прямой — 30 мин (потом «Авто» снова пробует быстрый путь);
  прямого успеха — 24 ч.
- Смена хоста эндпоинта инвалидирует знание автоматически: хост хранится внутри
  evidence и сверяется с текущим endpoint при чтении (без хуков в форме).
- TTL-записи имеют живого читателя (лестница + строка фактов карточки) —
  это принципиально: наблюдение без потребителя в этом кодbase уже удаляли
  один раз (capability-observer, шапка модуля).

Запись — только из `image-transport.js`, где известен истинный исход каждой
попытки: прямой POST ответил (любой статус) → очистка вердикта; прямой POST
упал с `IMAGE_DELIVERY_AMBIGUOUS` → «сломана»; оракул спас → «сломана».
Первый набросок писал успех/ambiguous из `image-api.js` по план-штампу — и
этот вариант содержал баг: после спасения оракулом план-штамп оставался
`direct`, и успех-хук затирал только что записанный вердикт. Транспорт не
кэширует стратегию и не меняет маршруты — запись опыта для него телеметрия,
как `recordDiagnosticEvent`.

### Слой 3 — preflight-оракул (`src/image-transport.js`)

Прямой JSON-POST с политикой `auto` упал с CORS/сетевым TypeError →
один дешёвый ручной OPTIONS к тому же URL (никогда не билится):

- OPTIONS не прошёл (TypeError или читаемый не-2xx; оба означают, что
  автоматический preflight упал бы тоже) → **POST доказуемо не отправлялся** →
  безопасная переотправка через `/proxy/` внутри того же вызова, перештамп
  `delivery='proxy'`, diagnostic `dispatch-fallback {reason:'preflight-oracle'}`,
  запись опыта «прямая сломана». Пользователь получает картинку в тот же клик.
- OPTIONS прошёл (читаемый 2xx) или таймаут/отмена → исход неоднозначен →
  прежнее поведение: `IMAGE_DELIVERY_AMBIGUOUS` + запись опыта. Дальше слой 2.

Это обобщение уже существующего паттерна `shouldFallbackToProxyJson`
(image-openai.js), который *предполагает* «preflight-фейл = ничего не ушло»,
не проверяя. Оракул проверяет. Отмена пользователем во время оракула
пробрасывается как AbortError; известный выключенный прокси отключает оракул.

## Сценарии (кратко; полная прогонка — в чате 2026-09-28)

- Провайдер без CORS (проба показала «через прокси»): первая генерация сразу
  proxy-first. Было: мгновенный ambiguous.
- ddtnew-кейс (GET прямой жив, POST умирает): первая генерация — оракул
  спасает в том же вызове (или один клик «Повторить», если OPTIONS прошёл);
  следующие ~30 минут — молча через прокси; потом самолечение обратно на direct.
- Очередь/повторы: доставка решается на каждом диспатче из свежего коннекта —
  задачи 2..N и «Повторить» подхватывают опыт без изменений в queue-коде.
- Смена хоста в карточке: знания сами становятся недействительными.
- «Сбросить знания о шлюзе»: стирает и `detected`, и `evidence`, и новый опыт.
- F5: опыт персистентен. Выключенный прокси: авто остаётся на direct.

## Часть 2: диалекты редактирования (multipart ↔ JSON ↔ img2img), 2026-09-28, вечер

Живой тест agnes (curl-матрица, мимо CORS) показал: их `/v1/images/edits` —
multipart-only (собственный 422: «'image' must be provided as a multipart file
upload»), наш JSON-диалект ими не реализован (500 missing 'image'), бэкенд
редактирования в момент теста лежал (503 no available server) — но
**`/v1/images/generations` принимает `image[]` из data URL и создаёт i2i-задачи**
(чистый JSON → проходит через ST-прокси). Референсы у agnes поддерживаются,
просто не тем диалектом, которым умеет расширение.

Отсюда диалектная цепочка для openai-images с референсами под политикой 'auto':

1. **multipart /edits напрямую** (классика) → CORS-смерть, доказанная
   OPTIONS-оракулом (экспортирован из image-transport) →
2. **JSON /edits через /proxy/** → HTTP-отказ диалекта (кроме 401/402/403/429 —
   те не диалектные факты) →
3. **generations + `image[]`** через /proxy/ → иначе типизированный
   `EDITS_DIALECT_EXHAUSTED` с обеими причинами.

Опыт — `editDialectEvidence` {host, multipartBlockedAt, jsonOkAt,
jsonRejectedAt, img2imgOkAt, ts}, TTL 30 минут, инвалидация по хосту,
«Сбросить знания» чистит; `editDialectHintFor` даёт стартовый диалект
(img2img/json) без повторного открытия. Проверки безопасности: 1→2 —
доказанно не ушёл; 2→3 — после HTTP-ответа (отказ диалекта, не рендер);
явные приказы (пин JSON, «Только напрямую», явный прокси) не участвуют —
shipped-фолбэк explicit-proxy сохранён без оракула. img2img-нога оборачивается
в exhausted только при HTTP-отказе; сеть/«200 без картинки» пробрасываются
как есть. Отказ img2img ничего не пишет (терминальная правда — в ошибке),
multipart-успех стирает все выученные пропуски.

## Аномалии, найденные при чтении (не всё чинится здесь)

1. README.md:70 обещал картинкам «next attempt goes through the ST proxy» —
   теперь правда; текст уточнён.
2. connect-probe.js:13 обещал «dispatch-plan can prefer it» — consumer
   появился (browserDeliveryRoute), сам dispatch-plan не тронут.
3. `shouldFallbackToProxyJson` (image-openai.js) делает безопасный ретрай
   multipart→JSON, *предполагая* preflight-фейл без проверки. Оставлено как
   есть (требует явного useCorsProxy-согласия), оракул мог бы его усилить —
   отдельная задача.
4. Fallback-ветка `fetchImageRoute` для GET достижима только из вызовов,
   которых нет в проде (все адаптеры зовут requestJson только с POST;
   скачивания — autoFetch, каталоги — catalogRequest). Оставлена: это
   связное спроектированное поведение под тестом, удаление сужает API.
5. `normalizeConnectionOverrides` кодирует «Авто» отсутствием поля — лестница
   обязана считать пустой override авто-режимом (учтено).
6. Два ambiguous-типа ошибок (DELIVERY_AMBIGUOUS ru / IMAGE_DELIVERY_AMBIGUOUS en).
   Код оставлен (пиннут тестами и capability-observer), сообщение стало
   русским и действенным, как у собрата.
7. Ошибка «CORS-прокси недоступен» (proxy.js) не имела типизированного кода и
   классифицировалась наблюдателем как `materialize` — «генерация прошла,
   упало сохранение», хотя POST мог вообще не уйти. Получила код
   `CORS_PROXY_UNAVAILABLE` и место в NETWORK_ERROR_CODES (→ network-unknown).
   Попутно вскрылось тестом pipeline-сериализации, чей счётчик считал все
   fetch-вызовы, а не платные POST.
