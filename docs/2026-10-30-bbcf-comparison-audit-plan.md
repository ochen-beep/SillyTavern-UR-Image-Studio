# Задача: аудит и code review UR Image Studio на фоне BB-Comic-Forge

- **Дата:** 2026-10-30
- **Статус:** задача сформулирована; экспресс-фаза выполнена (см. «Что уже сделано»), системная фаза не начата
- **Триггер:** пользовательский запрос «сравни BB-Comic-Forge и UR Image Studio, какое лучше сделано» — без цели, критериев и глубины. Эта док-ка заменяет расплывчатый запрос на проверяемое ТЗ.

## Цель

Ответить на три вопроса с доказательствами (file:line, запуск тестов, замеры), а не на слух:

1. **Честная позиция URIS** относительно стороннего расширения того же класса (BB-Comic-Forge v2.0.1): где мы сильнее, где слабее, что стоит украсть.
2. **Перечень конкретных дефектов и долгов URIS** с приоритетами P0–P3, пригодный для добавления в `2026-10-29-improvement-roadmap-plan.md`.
3. **Идеи для заимствования** из BB-CF (и обратное: что у нас сделано лучше — для понимания, не для гордости).

## Объект сравнения

| | UR Image Studio | BB-Comic-Forge |
|---|---|---|
| Репо | этот (v0.9.8) | https://github.com/maxkara14/BB-Comic-Forge (main, shallow clone) |
| Масштаб | ~33k строк своих + vendor, 119 модулей | ~10k строк, ~50 модулей |
| Класс | студия генерации картинок из чата (2-этапный промпт, инлайн-рендер, пайплайн, галерея) | верстальщик комикс-страниц (AI-черновик сцены → пер-панельная генерация → HTML-артефакт в чат) |

Классы пересекаются, но не совпадают: сравнивать «кто лучше» можно только по инженерным осям, не по фичам.

## Критерии сравнения (оси, вес одинаковый)

1. Архитектура и границы слоёв (UI / домен / транспорт / хранилище), размер и роль точки входа.
2. Надёжность: обработка ошибок, отмена, ретраи, поведение при платных генерациях, гонки (смена чата, две вкладки).
3. Работа с данными: где хранится, миграции, лимиты, целостность при переносе/мульти-писателях.
4. API-слой: контракты провайдеров, таймауты, очереди/пулы, деградация при отказах.
5. Безопасность и гигиена: экранирование, доверие сохранённому HTML, хранение и утечка ключей, логирование.
6. Тесты: количество, качество, что не покрыто, способ запуска, CI.
7. Документация: README/гайд/CHANGELOG, соответствие доков коду.

## Что уже сделано (экспресс-фаза, 2026-10-30)

Два параллельных ревью агентами, ключевые выводы спот-чеком подтверждены:

- **URIS сильнее:** точка входа 412 строк с ленивыми импортами (у BB-CF god-module на 1811 строк); 149 тестовых файлов против 7; слоистое хранилище (user-files API + шардирование + chatMetadata + localforage) против «всё в extension_settings»; двойная граница экранирования и redaction ошибок; комментарий-культура с датированными решениями.
- **URIS слабее / долги:** нет CI (тесты гоняются вручную — главный организационный долг); README.md:3 утверждает «keys in SillyTavern's secret storage», фактически ключи в localforage IndexedDB (`src/connection-store.js`); `core.js` — god-модуль на 1156 строк (план сплита есть, не выполнен); Web Locks между вкладками только предупреждает о конфликте, двойной расход денег возможен; stale-лог в `index.js` («Initialized v2 · catalog-v3» при 0.9.8).
- **BB-CF сильнее:** образцовый двуязычный README с mermaid и честными ограничениями; компактность (10k строк удерживаются в голове); фолбэки на уровне провайдеров (images-edit → text-only, Grok-повтор с image_url).
- **BB-CF слабее (на что не равняться):** доверие `innerHTML` к сохранённому HTML истории (вектор DOM-XSS при чужом settings.json); консольный API отдаёт настройки с plaintext-ключом; ядро генерации не покрыто тестами; версия manifest отстаёт от CHANGELOG.

## Системная фаза (не начата)

1. **Запустить полный тест-сьют** `npm test` (Node ≥ 22), зафиксировать время/падения/скипы; прогнать 3+ раза на предмет флаков.
2. **Пер-модульный ревью горячих зон:** `pipeline-stage1/2.js`, `pipeline-queue.js`, `image-transport.js`, `sharded-file-store.js`, `file-store.js`, `inline/runner.js`, `events.js` — на гонки, утечки памяти (unhandled rejections, неотвязанные подписки), поведение при отмене.
3. **Аудит денег:** все точки, где списывается оплата (платные POST), — проверить, что ни один путь не может задвоить генерацию (авто-триггеры + ручной клик + две вкладки + retry).
4. **Аудит безопасности:** grep-волна `innerHTML`/`insertAdjacentHTML`/`eval`/`new Function`; путь «чужой импорт настроек/пресетов → DOM»; подтверждение, что ключи не попадают в логи/нетдамп/экспорт.
5. **Сверка доков с кодом:** README.md (пункт про secret storage — исправить), USER_GUIDE.md, manifest-версия vs CHANGELOG.
6. **Замер заявлений о производительности** из roadmap (миниатюры пула 56–62ms и т.п.) — воспроизвести или пометить как непроверенные.
7. **Заимствования из BB-CF:** оценить перенос провайдерских фолбэков и формата честного README-раздела «Ограничения».

## Deliverable

- Отчёт в `docs/` (`2026-XX-XX-audit-report.md`): вердикт по 7 осям, таблица находок P0–P3 с file:line, список заимствований.
- Обновление `2026-10-29-improvement-roadmap-plan.md` пунктами из отчёта (или ссылки на них).
- Фикс рассинхрона README про secret storage — отдельным коммитом сразу, не ждать отчёта.

## Acceptance criteria

- Каждая находка имеет file:line и воспроизводимый сценарий либо тест.
- `npm test` прогнан, результат зафиксирован в отчёте.
- Нет находок без приоритета; P0/P1 имеют предложение по фиксу.
- Доки/код расхождения (как secret storage) закрыты или внесены в roadmap.

## Out of scope

- Ревью vendor-кода (photoswipe, croppr, fzstd).
- Фич-паритет с BB-CF (комикс-верстка — не наша ниша).
- Рефакторинг core.js в рамках аудита (существует отдельный план `2026-10-25-hygiene-split-plan.md`).
