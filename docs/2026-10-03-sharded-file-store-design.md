# Шардированное хранилище галереи и референсов — дизайн

- Дата: 2026-10-03
- Статус: принят к планированию (подход A — тайм-шарды + манифест)
- Затронутое: `src/file-store.js` (новый брат `createShardedFileStore`), `src/gallery-index.js`, `src/refs-library.js`, `src/ui/tab-gallery.js` (догрузка страниц), тесты

## Проблема

Галерейный индекс — один server-файл `uris_gallery.json` с массивом карточек.
При `mergeWithServer: true` каждая мутация (добавление, удаление, скрытие,
persist ширины/высоты) стоит GET всего файла + merge + POST всего файла в
base64. При заявленном масштабе 1000+ карточек это ~2–3МБ на каждый чих и
линейный рост. Открытие галереи тоже читает весь индекс целиком.

Референс-пул (`uris_refs.json`) — та же модель; растёт медленнее, но по тем же
правилам (неограниченный `description`).

`param-presets` и `studio` — маленькие конверты, шардинг им не нужен.

## Цели

1. Стоимость мутации — O(размер шарда) ≈ 250 записей, константа, не зависящая
   от размера пула.
2. Открытие галереи/референсов: параллельные GET мелких шардов вместо одного
   большого файла.
3. Внешние API `gallery-index.js` / `refs-library.js` не меняются вовсе:
   `createShardedFileStore` повторяет контракт `createFileStore`
   (`mutate`/`snapshot`/`replace`/`flush`), шардирование — внутренняя
   оптимизация записи (зеркало целиком в памяти, пишутся только «грязные»
   шарды). Ни один UI-файл не затрагивается.

**Фаза 2 (отложено):** ленивое постраничное чтение галереи. Код показал, что
`getGallery(chatId)` фильтрует весь индекс по чату, а лайтбокс ходит по полному
списку — честные ленивые страницы требуют индекса «карточек на чат» в манифесте
и переделки лайтбокса. Это отдельный цикл, возможно после мобильного прохода.

## Не-цели

- Append-запись: ST user-files пишет файлы целиком и атомарно — «дописать»
  нельзя, и не нужно.
- Компактация недозаполненных шардов (кроме удаления пустых).
- Ограничение размера одной записи (гигантский `description` референса —
  отдельная тема, сюда не входит).
- Формат записей: поля карточек (`ALLOWED` в gallery-index) и пул референсов
  не меняются. Меняется только то, где записи лежат и когда читаются.
- Пути картинок (`imagePath`, `thumbPath`) не трогаются вообще — шардируется
  только индекс метаданных.

## Файлы

```
uris_gallery_manifest.json
{
  "v": 1, "kind": "manifest", "store": "gallery",
  "shards": [
    { "id": "s0000", "count": 250, "minAt": 1750000000000, "maxAt": 1751000000000 },
    { "id": "s0001", "count": 213, "minAt": 1751000000001, "maxAt": 1752000000000 }
  ]
}

uris_gallery_shard_s0000.json
{
  "v": 1, "kind": "shard", "store": "gallery", "id": "s0000",
  "records": [ ...формат записи без изменений... ]
}
```

Референсы: `uris_refs_manifest.json` + `uris_refs_shard_*.json`, те же схемы.
Массивы-спутники малого размера (`folders` пула) живут в отдельном meta-файле
`uris_refs_meta.json` — обычный `createFileStore` с merge: у user-files нет
листинга директории, манифест должен восстанавливаться сканом шардов и не
несёт невосстановимых данных.

- Манифест всегда в памяти (строка на шард ~100Б; тысячи карточек — единицы КБ).
- `id` — `s0000`, `s0001`, … нулепаддинг, без пропусков: последовательность
  восстанавливается probe'ом `s0000, s0001, …` до первого 404 (листинга нет).
- `minAt`/`maxAt` — границы createdAt записей шарда (для вставки и порядка).

## Разбиение на шарды

- `SHARD_TARGET = 250` записей.
- Обычная вставка (генерация) → последний (самый новый) шард; в нём уже ≥
  SHARD_TARGET — открывается следующий.
- Bulk-вставка (импорт через data-port) раскладывает записи по их createdAt:
  место — бинарным поиском по `minAt`/`maxAt` шардов, при необходимости
  создаются «задние» шарды. Правило нужно, чтобы импорт не сваливал сотни
  старых карточек в один новый шард и не ломал ленивый порядок чтения.
- Шард, опустевший до 0 записей: строка убирается из манифеста, файл
  перезаписывается пустым `records: []` обычным serialized loop. Фактическое
  удаление файла — только если у user-files доступен DELETE-роут (см.
  «Открытые вопросы»). Прочей компактации нет.

## Операции

### Чтение (фаза 1 — жадно, обе стороны)

- `ready()`: GET манифеста → параллельные GET всех шардов → единое зеркало,
  байт-совместимое с сегодняшним (`snapshot`/`mutate` работают как раньше).
- `listCards()`, `listRefs()` и весь остальной API без изменений.

### Запись

- Мутация синхронно меняет зеркало и помечает «грязные» шарды (дифф по id
  записей: добавленные размещаются по правилам ниже, изменённые и удалённые
  помечают свои шарды). Serialized loop (как сегодня) пишет каждый грязный
  шард: GET шарда → merge (правила `mergeWithServer`, переиспользованный
  `mergeRecordArray`) → POST шарда; затем манифест, если менялись строки.
- Порядок записей в шардах заморожен при размещении: существующая запись
  никогда не переезжает между шардами. Массив шардов по id ASC = логический
  порядок зеркала.
- Размещение новой записи: в самый новый шард (front для галереи, end для
  референсов); он полон (≥ SHARD_TARGET) — открывается следующий. Запись с
  createdAt глубже диапазона нового шарда (пришедшая через merge с другого
  устройства) — бинарным поиском по min/max диапазонам в старый шард
  (переполнение разрешено, без расщеплений).
- Мульти-таб/мульти-девайс: merge-per-shard — семантики те же, что сегодня,
  payload меньше. Строки манифеста — производные данные: строка шарда,
  записанного этой сессией, побеждает строку чужого таба; чужие новые шарды
  добавляются в манифест как есть.
- `flushGalleryWrites` / `flushRefsWrites` (в т.ч. on unload) работают без
  изменений — новый стор регистрируется в том же реестре диагностики.

## Миграция

Триггер: манифеста нет, монолит есть и не tombstone.

1. GET монолита → раскладка по createdAt → POST всех шардов (идемпотентно —
   перезапись идентичного содержимого безопасна).
2. POST манифеста — **точка коммита**.
3. Монолит помечается tombstone: перезаписывается на
   `{ "v": 1, "kind": "migrated", "store": "gallery" }` (крошечный файл).
   DELETE-роут user-files не используется, чтобы миграция не зависела от
   непроверенной поверхности (при планировании можно проверить наличие
   удаления и сменить tombstone на удаление — tombstone остаётся фолбэком).

Прерывание на любом шаге до коммита: манифеста нет → миграция повторяется с
чистого состояния; монолит не тронут до полного успеха. Прерывание после
коммита: манифест есть → монолит-tombstone игнорируется, миграция завершится
записью tombstone при следующем запуске.

## Отказы

- Манифест бит или отсутствует, но шарды есть → пересборка манифеста probe'ом
  последовательности id (`s0000, s0001, …` до первого 404) с записью
  восстановленного манифеста. Манифест — производная структура, его потеря
  невосстановима только при потере самих шардов.
- Шард из манифеста не читается (404/битый JSON) → стор целиком `readonly` +
  диагностическое событие в INFO-ленту. Читать остальное можно, писать нельзя:
  merge-база неполна, запись могла бы молча потерять чужие правки. Никаких
  тихих потерь — принцип сегодняшнего file-store.
- Шард/манифест с `v` больше ожидаемого → этот файл readonly (старый код не
  «чинит» данные новой версии) — контракт текущего file-store сохраняется.

## Тестирование

Новый `tests/sharded-file-store.test.js`:

- раскладка вставок: append, переполнение шарда, bulk с задними createdAt;
- миграция: успех; прерывание до коммита → повтор; tombstone; монолит
  игнорируется при живом манифесте;
- merge-per-shard: правки второго таба не откатываются нашей записью;
  строка манифеста записанного шарда побеждает, чужие новые шарды сохраняются;
- сборка зеркала: порядок newest-first (галерея) и порядок вставки
  (референсы), без дублей и пропусков через границы шардов; размещение
  записи с createdAt вне диапазона нового шарда (merge с другого устройства);
- пересборка манифеста probe'ом последовательности; readonly при битом шарде;
  пустой шард перезаписывается пустым и уходит из манифеста;
- flush-on-unload пишет ровно грязные шарды (в пределах keepalive-лимита).

Регресс-щит «не сломали»: существующие тесты `gallery-index`, `refs-library`,
`file-store` проходят без ослабления ожиданий (внешнее поведение сохранено).
Тесты, монтирующие стор, получают новый набор файлов через существующие
`setXStoreForTests`-швы.

## Ожидаемый эффект

При 1000 карточек (~2МБ JSON): мутация ~0.5МБ JSON (~0.65МБ base64) вместо
~2.6МБ; открытие галереи ~0.5МБ вместо ~2.6МБ. При 5000 карточек стоимость
записи остаётся ~0.5МБ (сегодня — ~13МБ на мутацию).

## Открытые вопросы (разрешить при планировании)

- Наличие DELETE-роута у ST user-files — решает, tombstone или удаление.
- `SHARD_TARGET = 250` — переоценить по замерам на реальном индексе.
